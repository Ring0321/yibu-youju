## 0. 执行摘要

**确定路线：以成熟全栈工程为基础，接入真实模型和审核知识，开发独立的服务状态、反例审查与验效内核，并配套可实际接单的人工工作台。**

工程采用模块化单体，首版单组织运行，不做多个独立微服务。业务接口和后台任务共用代码与数据库；用户端、客服端、知识审核端共享权限体系。前端不计算结案结果、不伪造业务回执。

| 决策 | 本计划确定的做法 |
| --- | --- |
| 工程基础 | 复用 FastAPI 官方全栈模板的前后端工程、数据库迁移、登录基础、接口客户端和测试结构 |
| 流程执行 | 复用 LangGraph 的有状态流程与持久化能力；业务事实以应用数据库为准 |
| 知识检索 | PostgreSQL + pgvector；产品、地区、版本和有效状态先过滤，再召回与排序 |
| 资料解析 | Docling 离线导入；审核后才发布，不让实时问答请求承担文档解析 |
| 后台任务 | 采用 PostgreSQL 任务队列 Procrastinate，承担模型、导入和可重试处理；先完成兼容与崩溃恢复验证 |
| 核心自研 | 产品验证契约、证据适用性、动作影响更新、相容反例、复测选择、结论等级 |
| 人工闭环 | 首版内置精简真实工作台；后续按需要接企业系统或 Chatwoot，而不是首版同时部署另一套平台 |
| 测试方式 | 逻辑单测 + 真实数据库集成 + 真实模型冒烟 + 双用户端到端 + 故障恢复与实机验证 |
| 完成标准 | 任何“已保存、已识别、已提交、已接单、已验证”都有可回查的真实记录 |

**可行性结论：有条件可行，当前可以启动技术验证，尚不能承诺交付时间或实际维修效果。** 独立复审确认 v7 的 152 人时加总无误，但缺少专门的数据准备、早期实机规程验证和运营工作，且 24 小时裁剪范围不可核算。v8 取消“11 至 15 个工作日即可完成 L2”的口径。

**修订排期：** 第 9 节列出 41 个工作包，核心开发估算 230 至 352 人时，另留 20% 非预期返工机动，约 276 至 422.4 人时。约 3 人且每天各投入 5 至 6 个有效小时，按职责瓶颈和依赖先预留 4 至 7 个开发周，再在 G0 后重估；专业审核、设备、数据与客服值守另列资源，外部等待不计入开发人时。

24 小时是通过 G0、资源就绪且复用获准后的条件性 L1 挑战目标。第 10 节单列 18 项、50 人时的裁剪排程；没有计时演练和必测记录，不宣称已经证明可以按时完成。企业上线另外验收。

## 2. “真实可用”的定义

### 2.1 必须跑通的完整过程

1. 真实用户登录或获得受控访问身份，创建属于自己的服务会话。
2. 提交自由描述和真实图片，文件实际存储，上传失败有明确提示。
3. 后台调用真实模型，记录调用状态与版本，提取产品和症状候选；识别不了时允许用户纠正。
4. 系统确认产品后检索适用且已审核的资料，指导内容可定位到来源。
5. 用户执行一个适用步骤，报告完成、未完成、部分完成或无法执行。
6. 后台记录操作，更新相关证据与候选状态，不靠前端变量假装状态变化。
7. 验效模块判断当前结论能否成立；必要时选择复测，无法验证时保留待验证。
8. 需要人工时实际创建内部服务单，客服用另一个账号看到、接单、补问并处理。
9. 用户能看到真实处理进展；刷新页面、重新登录或服务重启后不会丢失已提交内容。
10. 全程的来源、状态、模型调用、人工操作和结论等级可回查。

### 2.2 三个交付等级

| 等级 | 用途 | 可以承诺 | 不可以承诺 |
| --- | --- | --- | --- |
| L1：受限运行版 | 赛场与受控体验 | 真实模型、真实资料、真实数据库和内部人工接单；单型号故障族 | 自动证明物理修复、全品类支持、企业正式质保处理 |
| L2：小范围试用版 | 邀请真实用户使用 | 完成权限、恢复、导入审核、隐私处理、测试和受控实机验证 | 未经组织授权的官方售后身份与企业生产保证 |
| L3：企业上线版 | 企业真实业务 | 经授权接口、正式运营责任、监控和安全验收下的服务 | 由开发团队自行宣告通过企业验收 |

**没有实机并不妨碍建立真实软件服务，但等级仍为 L1，不能通过包含物理条件的 G5/L2。没有企业接口也不妨碍内部真实接单，但必须写明“项目客服”，不能冒充 Anker 官方客服。** L1 面向受控邀请和明确值守时段，不等于可公开长期运营。

## 3. 命题与设计对应表

| 命题要求 | 可操作实现 | 验收证据 | 首版边界 |
| --- | --- | --- | --- |
| 理解文本、情绪与紧迫性 | 提取用户明确表达的焦急、使用期限、操作限制，调整单步信息量 | 原始描述、提取字段、可纠正入口、后续路径 | 不从一张人脸图推断心理状态；情绪不改变安全与质保标准 |
| 多模态理解 | 产品外观、铭牌、报错界面和局部状态的候选提取 | 真实模型请求记录、素材引用、识别失败样本 | 不把不可见内部状态当作已知 |
| 产品消歧 | 产品目录、别名、图文候选与用户确认 | “S1 Pro 不吸了”必须先确认类别 | 吸奶器只支持类别澄清与转交，不直接套用扫地机流程 |
| 技术知识库 | 已审核文档分块、产品过滤、检索与来源定位 | 引用能回到原始段落及有效版本 | 原始网页和模型生成规则不能自动发布 |
| 历史工单 | 授权范围内检索同一用户或经脱敏批准的案例 | 权限测试、访问记录、引用的历史案例 | 不能暗示已获得 Anker 私有工单 |
| 故障定位与指导 | 两类有官方依据的排查方向，逐步执行 | 每一步有来源、前提和反馈，未知有出口 | 不自行新增电机故障等无依据分支 |
| 服务闭环 | 结果等级、内部真实工单、人工接续 | 双账号真实接单与用户端同步 | 内部回执不等同于企业系统回执 |
| 渠道与质保 | 记录购买渠道、凭证和查询状态，人工核对 | 未找到订单不会自动判为不保修 | 无授权接口时明确“尚未核验”，不返回假查询结果 |
| 流程与规则结合 | 受控工作流调用独立验效内核 | 非法跳步、证据不足和重复请求测试 | 模型不得直接修改权限或最终业务状态 |
| 创新与复用 | 相容反例、有效复测、验证契约 | 反例用例、强基线对照、第二产品适配记录 | 既有框架能力不宣称为自研算法 |

S1 Pro 首版资料依据为官方吸力下降支持页，涉及残留物阻塞和护条/密封等部位问题。它没有提供本项目可直接采用的客观恢复阈值。具体操作、安全注意与复测规程还需完整手册及专业审核。 [官方支持资料](https://service.eufy.com/article-description/What-should-I-do-if-my-S1-Pro-s-suction-becomes-weak)

### 4.3 复用接入必须遵循的流程

1. 记录仓库 URL、完整提交 SHA、许可证和所用目录；在独立分支导入模板，不覆盖既有研究文件。
2. 查看安装脚本、容器构建、默认账号、遥测和自动部署配置；不直接运行来源不明的一键部署脚本。
3. 保留 LICENSE、必要 NOTICE 和第三方来源说明；不得将上游界面及核心能力整体署名为自主研发。
4. 上游模板示例 `.env` 只做字段参考，真实密钥只进入未提交的本地配置或受控密钥系统。
5. 先运行上游基础测试，再加入依赖与新业务；每次升级都重新验证迁移、权限、恢复与关键流程。
6. 固定 Python/Bun 依赖锁及容器镜像摘要。下文 SHA 是调研快照，不等于所有主分支提交都适合直接用于生产。

### 4.4 已发现的兼容与恢复风险

模板抽查提交的后端要求 `Python >=3.14`，镜像采用 Python 3.14，前端构建采用 Bun；前端清单已有 Playwright `1.62.1`。保留模板的构建方式，不同时引入另一种包管理器。 [后端清单](https://github.com/fastapi/full-stack-fastapi-template/blob/cb740b656d7a0a6c5e12c7bf8e50343ec94ee9c7/backend/pyproject.toml)、[构建文件](https://github.com/fastapi/full-stack-fastapi-template/blob/cb740b656d7a0a6c5e12c7bf8e50343ec94ee9c7/backend/Dockerfile)、[前端清单](https://github.com/fastapi/full-stack-fastapi-template/blob/cb740b656d7a0a6c5e12c7bf8e50343ec94ee9c7/frontend/package.json)

LangGraph 抽查源码标注核心包 `1.2.12`、PostgreSQL 检查点包 `3.1.2`；这些是源码声明，发布可用性和依赖组合仍须在 G0-S 验证后锁定。恢复时节点可能从头执行，检查点不等于外部操作恰好执行一次。 [中断文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

任务队列也不能默认“进程被杀后会自动安全重跑”。Procrastinate 文档明确需要处理失联任务；本项目必须实现心跳检查、有限重试与业务幂等。 [失联任务处理](https://procrastinate.readthedocs.io/en/stable/howto/production/retry_stalled_jobs.html)

## 5. 系统架构与职责

### 5.1 部署组成

| 组成 | 内容 | 首版部署方式 |
| --- | --- | --- |
| Web | 用户服务、客服工作台、知识审核 | React 构建产物随应用部署，同源访问 |
| API | 身份、会话、素材、状态、人工服务、知识管理 | FastAPI 应用进程 |
| Worker | 模型调用、流程执行、资料解析、任务恢复 | 同一代码库的独立后台进程 |
| 数据库 | 业务记录、事件、向量、任务、检查点 | 一个 PostgreSQL 实例，表或 schema 明确划分 |
| 素材存储 | 图片和文档原件 | 首版专用持久卷，数据库存元数据；多实例前迁至私有对象存储 |
| 入口 | HTTPS、请求大小和基本访问限制 | 受控反向代理；数据库与管理端口不暴露公网 |

L1 不部署 Kubernetes、Kafka、独立图数据库、额外向量库或多个 Agent 平台。离线解析可单独构建镜像，避免重型解析依赖进入在线问答容器。

### 5.2 四条责任边界

1. **模型理解，不做最终业务提交。** 可以提出产品候选、局部观察与建议表达；不能设置证据可信等级、审批结果或已接单状态。
2. **数据库保存事实。** 所有用户提交、人工确认与状态变更先成为可持久化事件；检查点不是另一份拥有最终解释权的业务数据库。
3. **验效模块决定结论等级。** 只接受符合模式、来源和权限要求的输入，返回结构化结果及不足依据。
4. **业务适配器执行外部动作。** 订单、工单和通知经授权、幂等与回执检查，不由大模型拼接 URL 任意调用。

### 5.3 一次真实请求的时序

1. API 校验身份、会话归属、文件归属与 `expected_version`，检查 `Idempotency-Key`。
2. 在同一个数据库事务中写入用户事件、更新会话版本并写 outbox；返回真实 `event_id` 和 `run_id`。
3. outbox 投递后台任务，重复投递允许发生，但 `run_id` 与步骤执行记录必须去重。
4. Worker 读取当前版本，调用模型或检索；网络等待期间不持有长时间业务行锁。
5. 输出先经模式与权限校验；若会话版本已被用户新输入或客服接管改变，旧结果不得覆盖新状态。
6. 验效模块运行，事务性保存决策、证据引用和下一个允许操作；更新任务状态。
7. 前端通过受鉴权的事件流或轮询获取后端状态；断线后按事件序号补取，不重复触发模型调用。

检查点保存 `case_id`、输入事件、步骤位置及相关版本，业务事件保存事实。两者写入不能假定天然跨事务原子；每个节点通过幂等业务服务读取或取得已保存结果，重放时先核对业务版本和步骤记录。

## 6. 数据模型与状态规则

### 6.1 核心数据表

| 表/对象 | 关键字段 | 作用 |
| --- | --- | --- |
| `users` / `memberships` | 身份、角色、组织、禁用状态 | 用户、客服、知识审核员和管理员权限 |
| `products` / `product_aliases` | 品类、型号、别名、地区、适用版本 | 消歧与资料范围 |
| `service_cases` | 所有人、产品、流程状态、版本、契约版本、当前负责人 | 售后会话主记录 |
| `case_events` | 会话、顺序号、事件类型、操作者、输入版本、幂等键 | 业务历史与状态重放 |
| `assets` | 所有人、存储键、哈希、格式、大小、上传状态、声明拍摄时间 | 原始文件与访问控制 |
| `observations` | 素材引用、谓词、值、来源类型、候选/确认状态、确认人 | 区分模型推断和已核实记录 |
| `actions` / `action_reports` | 动作实例、前提、影响范围、用户报告、实际时序 | 区分建议发出与执行反馈 |
| `documents` / `document_versions` / `chunks` | 来源、内容哈希、版本、适用范围、审核状态、定位、向量 | 可回查且可回滚的知识 |
| `service_packs` / `pack_versions` | 状态模型、动作、观察能力、结果条件、批准人 | 可执行验证契约 |
| `decisions` / `verification_records` | 输入版本、剩余反例、检查、依据、结果等级 | 可解释验效记录 |
| `service_tickets` / `ticket_events` | 内部单号、状态、接单人、消息、业务回执 | 真实人工处理闭环 |
| `model_runs` / `step_runs` | 请求引用、模型/提示版本、用量、耗时、状态、重试 | 诊断、成本和幂等结果缓存 |
| `outbox` / `integration_receipts` | 操作键、适配器、投递次数、远端单号、回执状态 | 跨系统一致性与异常补偿 |

派生的会话快照可以重建；原始事实采用追加更正事件，不偷偷覆盖历史。审计记录本身不是防篡改证明，数据库管理员仍有能力修改数据；正式审计要求另行设计。

### 6.2 必须建立的约束

- 同一会话事件序号唯一；同一幂等键重复提交相同请求返回已有结果，不同内容返回冲突。
- 所有会话、素材、工单查询先做组织与所有权检查；不能只凭随机 ID 难猜测来保护数据。
- 用户端不能提交 `trusted=true`、`verified=true`、任意 `role` 或最终结案状态。
- 动作反馈必须绑定具体动作实例，不能把上一轮“做完了”归到新动作。
- 模型输出必须带 `input_case_version`；过期结果保留为历史，不应用到当前状态。
- 同一照片与其 OCR 是一个来源组；不同图片也不自动按统计独立处理。
- 没有可靠拍摄顺序依据时标注未知；上传时间、EXIF、任务口令均不单独证明照片真实性。

### 6.3 流程状态与结果等级分开

流程状态建议为 `INTAKE`、`NEEDS_PRODUCT_CONFIRMATION`、`TRIAGING`、`WAITING_USER_ACTION`、`WAITING_VERIFICATION`、`HUMAN_QUEUE`、`HUMAN_ACTIVE`、`CLOSED`。

结果类型另存：`PENDING`、`USER_REPORTED_RECOVERY`、`LOCAL_OBSERVATION_ONLY`、`PROTOCOL_RESULT_SUPPORTED`、`UNRESOLVED`、`OUT_OF_SCOPE`、`EVIDENCE_CONFLICT`。关闭会话不代表修复成功，关闭原因必须单独记录。

`PROTOCOL_RESULT_SUPPORTED` 仅代表在指定规程、环境和证据范围内得到支持，不能翻译成“设备完全正常”。未建立真实复测规程时关闭该结果类型的自动进入路径。

人工接单使用独立事件与身份记录。分配给某客服不代表客服已经接受处理，必须有真实接单动作。

业务流程状态不复用队列状态。后台运行另有 `PENDING`、`RUNNING`、`WAITING_INPUT`、`COMMITTED`、`CANCELLED_STALE`、`FAILED_REQUIRES_REVIEW`。等待用户时结束当前队列任务并保存可恢复位置，不维持一个永久 `doing` 的工作任务。

## 7. 核心模块如何实现

### 7.1 多模态理解与模型适配

定义一个模型接口，统一文字、图片、结构化结果、超时和用量记录。先接一个具备图片理解与结构化输出能力的真实供应商；模型名称根据实际账号权限确定，不在未验证时写死某个“最新最强”型号。

结构化输出包括 `product_candidates`、`symptoms`、`reported_actions`、`visible_observations`、`user_constraints`、`urgency_cues`、`missing_information`。每项带原文或素材引用，不允许无来源字段悄悄进入当前事实。

不训练基础模型。先用 20 至 30 条图文样例筛查适用性，再制作开发集与独立保留集。图片拒识、模糊、不可见以及产品不匹配必须是正常输出。

每轮调用上限、允许工具和停止条件统一以 7.11 节执行协议为准。优先结构化理解加确定性渲染；超时、限流、预算不足时降级到审核步骤或人工，不展示编造的模型分析。

### 7.2 知识导入与检索

导入路径：人工批准的 URL/文件 → 解析 → 来源与产品元数据 → 分块 → 审核 → 嵌入 → 发布版本。

先限定官方支持资料和用户授权文档，不运行开放网页自动搜答案。图片、PDF 和网页内容不被视为可执行系统指令。管理端链接抓取禁止访问本机、内网和云元数据地址，并重新检查跳转目标。

分块保留完整动作、注意事项与前提，不能将“不要执行”与后面的动作拆开后单独召回。每块有标题路径、段落/页码、原始 URL、内容哈希和版本。

检索先按产品、品类、地区、固件/资料适用版本和发布状态过滤，再组合型号/错误码匹配与向量召回。中文查询不能直接假定英文全文检索配置有效；首版用明确别名和型号匹配配合多语嵌入，必要时经对照后增加中文分词检索。

小知识库优先精确向量扫描，达到数据规模与延迟要求后再配置近似索引。切换嵌入模型时新建对应版本索引，禁止混用不同向量维度或语义空间。

检索片段用于解释与受控规则选择，不允许模型临时创造维修操作。引用验证器检查来源 ID 存在、适用且为当前准许版本；无适用来源时进入未知出口。

### 7.3 验证契约与发布

每个服务包至少包含产品范围、状态谓词、允许动作、动作前提、影响集合、可能执行结果、观察能力、结果类型、功能复测规程、禁止动作和未知出口。

采用模式校验的 JSON/YAML，禁止嵌入任意代码或使用 `eval`。包发布需审核人批准、记录版本、执行反例测试。正在进行的会话固定契约版本；遇到安全撤回时立即阻止相关操作并转人工，而非静默沿用旧危险规则。

模型可以协助提出规则草稿，但“来自说明书”不等于“模型提取无误”，必须逐条检查动作、否定表达、条件与来源。

### 7.4 自研验效内核

输入是已确认产品、契约版本、事件、观察和允许检查；输出为剩余候选状态、尚未排除的反例、可用检查、阻断原因和结果等级。

实现顺序：

1. 将现有合成模块改成可传入领域配置的纯函数；保留原测试，但取消写死的产品与功能定义。
2. 对“未执行、部分执行、正确执行、执行结果未知”分别定义允许结果，不自动应用理想动作效果。
3. 依据动作影响重审证据；保留不受影响事实。一个结论有多个有效支持时不因撤销一条就必然变假。
4. 搜索与当前有效观察相容、但目标结论不成立的状态；有反例就不得输出该高等级结论。
5. 从安全且当前可执行的检查中选择有区分能力者；仅反复描述同一来源没有额外价值。
6. 处理空候选集合、模型外异常、观察模糊、缺少规程、用户不能执行和状态空间超限。
7. 对允许结论再检查独立的功能复测与来源等级条件，防止局部外观推断绕过结果契约。

首版候选状态建议上限 64、检查上限 8，这只是实现预算，不是性能保证。超限返回受限处理/人工，不能删掉不利状态获得“已恢复”。包含设备操作的检查不是无副作用查询，必须执行一步后重新规划。

**关键设计修正：** 某检查不消除反例，却是验效规程强制项时仍须执行。不能仅因为区分分数为零就跳过必要功能复测；“必要规程”和“可选信息增益”分别处理。

真实产品中须区分两类目标：排障假设用于选择指导，限定规程结果用于评价本次观察。不能因为已列举的两个故障方向被排除，就认定所有可能故障都不存在；反例搜索的保证只覆盖审核模型，不覆盖未知物理世界。没有合格功能规程时，真实会话禁用高等级规程结论路径。

### 7.5 历史记录与隐私

同一用户可查看自己的历史会话；客服仅查看被授权的工作队列或会话；公开知识只能使用审核脱敏案例。未经授权的跨用户历史不进入检索。

交接摘要由结构化记录生成：产品、症状、已执行动作、未确认信息、失败检查、引用证据、当前结果等级。AI 可润色，但不得将“用户自述”改写成“已证实”。

### 7.6 内部人工工作台

首版必须实现真实队列、原子接单、追加消息、请求补充信息、记录处理结果及关闭/重新打开。两名客服同时接单时只能一人成功，失败方看到最新状态。

客服接管后 AI 暂停自主推进操作，仅作为建议辅助。重新交回自动流程须显式记录，旧 Worker 输出不得覆盖客服操作。

增加可用时段和接单承诺配置。区分“可以提交材料”“等待排队”“已被真人接单”和“当前无人值守”；未登记真实值守人员时关闭面向公众的服务入口。超出接单承诺或接单者离线时通知指定备岗并允许重新分配，不能继续显示“客服正在处理”。不填写未经责任人确认的响应时间承诺。

这使系统无需等待企业 API 也能真实闭环。企业接口适配不与人工工作台混成一个假按钮。Chatwoot 等外部接入需要远端真实会话回执，并区分远端创建、分配与接单。 [外部会话 API 参考](https://developers.chatwoot.com/api-reference/conversations/create-new-conversation)

### 7.7 渠道凭证与质保路径

建立购买渠道、凭证附件和核验状态，不自动裁定质保。订单查询适配器必须区分 `MATCHED`、`NOT_FOUND`、`UNAVAILABLE`、`UNAUTHORIZED` 和 `ERROR`。

无官方接口时，只提供材料收集及人工核对。测试商家列表标注为测试数据；运营方自行维护的真实名录标注来源和更新时间，不自称官方授权名录。


### 7.8 产品智能体：职责与可执行范围

产品内只设置一个面向用户的有状态服务执行智能体，名称为 `ServiceAgent`。它由多模态理解、受限工具选择、结构化提案和流程暂停能力组成；验效器、权限检查器和事务提交器是确定性程序，不包装成三个会聊天的 Agent。

其自主性限于：在当前允许集合中选择澄清内容、检索请求和下一步提案。它不能自由创建维修操作，也不能自行认定恢复。固定流程仍承担安全和结论底线；自由输入到受控行动的映射，是模型需要通过测试证明的价值。[工作流与 Agent 的官方区分](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

| 对象 | 允许承担 | 不允许承担 |
| --- | --- | --- |
| `ServiceAgent` | 理解描述和图片、选取适用只读工具、提出单步交互、解释系统判定 | 直接写可信等级、改权限、审核规则、退款、凭空生成维修步骤 |
| `VerificationKernel` | 执行状态更新、反例检查、必要复测和结论等级规则 | 将未审核物理假设当作产品真实规律 |
| `PolicyGate` | 检查角色、来源、产品范围、当前版本、允许操作和确认凭据 | 因模型表示“很确定”而放行 |
| `CommandService` | 在事务中提交获准业务变化，返回真实记录 ID | 把网络成功或模型回答当作远端业务已完成 |
| 真人客服 | 在授权范围内接单、补问、确认处理结果 | 用一个确认按钮把缺失的测量或规程条件伪造成存在 |

本轮另行安排的独立评审智能体用于开发计划审查，不加入每轮客服请求，不带来额外在线模型调用，也不是具有统计独立性的第二位专业鉴定人。

### 7.9 智能体输入、提案与执行结果

由服务端组装 `AgentContext`，包括：当前操作者权限、会话/设备身份、业务版本、接管代次、产品服务包版本、已核实记录、候选记录、适用知识引用、允许提案集合、待完成确认和剩余预算。角色、组织和可信来源由服务器读取，绝不接受模型或客户端自报。

模型只返回 `AgentProposal`。未知字段拒绝；ID 必须来自当前上下文；枚举不允许自由扩展。下面只是接口设计示例，不是已运行的业务回执：

```json
{
  "schema_version": "1",
  "input_case_version": 12,
  "proposal": {
    "kind": "OFFER_HANDOFF",
    "target_ref": null,
    "reason_code": "NO_APPROVED_FUNCTIONAL_CHECK",
    "evidence_refs": ["obs_local_03"],
    "knowledge_refs": ["chunk_approved_07"]
  },
  "missing_information": ["functional_check_result"],
  "user_message_draft": "现有照片只能支持局部外观判断。当前缺少可用的功能复测条件，可以将已尝试步骤交给客服继续处理。"
}
```

真实返回给前端的是服务端生成的 `ExecutionOutcome`，至少包含 `proposal_id`、`gate_status`、`decision_id`、`committed_event_id`、`case_version`、`result_grade`、`next_allowed_action` 和 `error_code`。只有事务成功后才填提交记录。被拒绝的提案不能通过回复文案继续展示为已经完成。

模型的解释只保留简短理由、来源和缺失条件，不要求或保存隐含思维过程。医疗判断、危险内部维修、退款和最终质保判定不进入首版提案枚举。

### 7.10 工具权限与提交规则

| 工具或命令 | 调用者 | 输入边界 | 真实返回 / 副作用 |
| --- | --- | --- | --- |
| `get_case_snapshot` | 服务端；智能体获裁剪结果 | 从当前身份绑定会话，不由模型指定任意用户 | 当前版本、授权记录，无业务写入 |
| `lookup_product` | 智能体可提议 | 用户描述中的别名/类别；限制返回条数 | 产品候选，不自动确认产品 |
| `search_approved_knowledge` | 智能体可提议 | 已确认产品与地区由服务端注入 | 已发布片段及引用；不能传任意 URL |
| `list_allowed_steps` | 服务端 | 当前契约、前提、禁忌和用户限制 | 可提议动作/检查的 ID 集合 |
| `assess_claim` | 服务端确定性调用 | 当前有效记录、指定限定结论 | 结果等级、阻断项、相容反例，不执行物理动作 |
| `build_handoff_preview` | 智能体可提议 | 当前会话内事实、报告和未确认项 | 交接预览，不生成“已接单”状态 |
| `publish_next_step` | 提交器 | 获准提案、当前版本、动作来源 | 保存一个下一步及事件；设备仍由用户操作 |
| `submit_internal_handoff` | 提交器 | 用户明确确认的预览、版本与幂等键 | 创建一个真实内部服务单，不等于真人接受 |
| `accept_ticket` / `resolve_ticket` | 授权客服 API | 客服身份、工单状态与结果依据 | 接单或处理记录；不向模型开放直接调用 |

首版不配置自由浏览器、任意 SQL、Shell、无约束 HTTP 或跨用户记忆工具。知识中的“请执行某命令”、图片文字或订单附件都属于数据，不能改变工具权限。提示词提醒只是辅助；权限和参数校验必须在模型外执行。[提示注入风险与边界](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

需要用户确认的命令绑定 `proposal_id + expected_version + preview_hash + expiry`，确认凭据由后端签发并限定当前用户。内容、产品或接管状态发生变化后原确认失效。内部建单幂等键与一次业务意图绑定；同键不同内容必须冲突，不能返回看似成功的旧单。

### 7.11 一轮运行的明确协议

1. 接收并持久化输入，锁定输入业务版本；为同一会话安排顺序处理。网络调用不持有数据库行锁。
2. 先做安全、接管、产品范围和预算检查。已接管时停止自动提出设备操作，只向客服提供辅助。
3. 调用模型提取候选；需要工具时仅调用当前获准的只读工具，返回范围经过服务端过滤。
4. 运行验效器，形成允许的澄清、动作或检查集合；必要规程优先于可选检查收益。
5. 模型提出一个下一步，或使用确定性模板直接表达。提案不直接改写业务事实。
6. 校验提案模式、引用、允许 ID、内容安全、当前版本和接管代次；用户确认缺失时进入等待，不长期占用 Worker。
7. 提交器在短事务中再次比较版本和代次，保存决策及事件；任一条件变化则拒绝旧提交，重新读取状态。
8. 向前端返回真实结果；停止本轮并等待用户、真人客服或受控恢复事件。不在无新信息时持续自我对话。

正常一轮最多两次模型调用：理解一次，以及确有必要的工具结果解释/提案一次。格式修复最多额外一次，全部尝试合计硬上限三次；不再另加独立润色调用。只读工具最多四次，单轮总执行期限初始设为 90 秒，单次模型请求试验超时为 45 秒，后续按真实测量调整。

达到硬上限、连续两轮没有新增有效信息、检查不可执行或用户要求人工时，停止主动规划，显示受限原因和人工选项。同一检查的不可执行记录不能被下一轮遗忘。涉及物理操作时每轮最多提供一个经审核步骤，执行反馈后重新规划。

### 7.12 观察确认不能越过证据边界

| 输入及确认 | 可以进入的记录 | 不能据此得出的结果 |
| --- | --- | --- |
| 用户说“清理完成”，并确认转写正确 | 已确认的用户报告 | 已正确完成全部动作、功能恢复 |
| 用户选中产品类别和型号 | 用户确认的身份信息，仍标注来源 | 厂家系统已认证设备或订单 |
| 模型从照片识别到局部外观，用户表示同意 | 用户确认的局部观察报告 | 不可见内部状态、真实拍摄时序或客观吸力 |
| 授权审核员查看符合要求的素材 | 审核范围内的局部观察 | 范围外性能及未观察部位正常 |
| 经批准规程、合格采集条件和必要结果记录 | 由规则计算的限定规程结果 | 永久修复、所有功能无故障 |

实现时分别存储 `record_type`、`reported_by`、`reviewed_by`、`capture_context`、`scope` 和 `support_status`，避免用一个 `confirmed=true` 混淆“确认说过”与“证实物理状态”。证据不足时，即使所有已建模状态都支持结论，也不能绕过功能规程要求。

### 7.13 恢复与并发的执行约束

业务数据库是事实来源；LangGraph 仅恢复计算位置和引用。接管、归还自动处理、取消会话及安全撤回均使对应控制版本失效。旧任务即使仍在运行，也不能用旧版本提交。

恢复时节点可能从头执行，因此提交节点前后都要检查既有步骤结果；不能因把写操作放到暂停之后，就假定任何崩溃重试都只执行一次。[中断与重放文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

| 故障窗口 | 恢复动作 | 必须验收的不变量 |
| --- | --- | --- |
| 输入事务已提交、队列未收到任务 | outbox 重新投递，任务键去重 | 输入不丢、业务事件不重复 |
| 模型已返回、步骤结果尚未持久化 | 允许有限重算，记录重复成本 | 不声称外部模型调用恰好一次 |
| 业务已提交、检查点未更新 | 从步骤记录读取既有结果，推进计算 | 不重复发布步骤或重复建单 |
| 检查点提示已完成、业务记录不存在 | 禁止推定成功，进入一致性修复 | 前端不显示不存在的业务回执 |
| Worker 失联后旧进程恢复 | 新租约/执行代次控制提交，旧代次拒绝 | 不出现两个有效提交者 |
| 客服接管或契约撤回与模型返回同时发生 | 提交事务复查控制版本与撤回状态 | 安全与人工优先于旧模型结果 |

同一会话原则上只允许一个计算任务进入提交阶段；仍用版本比较防护重放、超时旧任务和人工并发。实现应使用数据库条件更新/锁以及唯一约束，不能仅靠进程内锁。[PostgreSQL 并发事务语义](https://www.postgresql.org/docs/current/transaction-iso.html)

队列失联恢复需要运行中的维护进程或容器重启后的恢复扫描。所有 Worker 都停止时，队列不会自行处理。失联阈值必须结合心跳、长模型请求和容器暂停测试；不得用“执行时间长”直接判定可重试。[队列失联文档](https://procrastinate.readthedocs.io/en/stable/howto/production/retry_stalled_jobs.html)


合法组合另作显式规定：

| 业务状态 | 运行状态 | 队列 / 检查点 | 恢复负责人及动作 |
| --- | --- | --- | --- |
| 等待用户操作/确认 | `WAITING_INPUT` | 队列已结束；检查点暂停 | 不算失联，不自动重试；新用户事件经鉴权恢复 |
| 已接收但未执行 | `PENDING` | 待投递/排队 | outbox 投递器负责入队，保持原业务键 |
| 处理中 | `RUNNING` | Worker 有效心跳、租约有效 | 不由超时扫描直接抢占；超总期限则撤销提交资格 |
| 步骤业务已提交 | `COMMITTED` | 检查点可能落后 | 读既有步骤结果补齐计算位置，不重复业务写入 |
| 已人工接管 | `CANCELLED_STALE` | 旧任务可能仍返回 | 拒绝旧控制代次；真人状态不被覆盖 |
| 达到重试/期限上限 | `FAILED_REQUIRES_REVIEW` | 无自动新尝试 | 显示可恢复失败与人工入口，禁止无限入队 |

由唯一的恢复协调器在数据库锁保护下申领失联运行并更新执行代次；运输层重复投递不等于获得业务重试权。每个 run 的调用预算和截止时间持久化，队列重试不能重置预算。恢复扫描先区分合法等待、可重试只读计算、结果不明的外部写操作；后者进入核对队列。

候选初值为每个运行最多两次自动恢复尝试，且仍受原模型调用总预算及原截止时间约束；重试耗尽即停。验收须记录失联到恢复/明确失败的实际时间，长任务与暂停容器测试通过前不把阈值当作可靠运行参数。

### 7.14 智能体的最小验收轨迹

用一条自由描述和一张真实图片启动：产品不确定时只澄清；确认后引用适用资料；用户报告部分执行时保留未完成可能；照片显示局部改善时不升级为功能恢复；没有合格复测条件时提出交接。用户确认后创建内部单，另一客服账号接单并续聊，刷新和服务重启后历史仍在。

每一步同时核对 `case_event`、模型调用、工具返回、规则判定与页面内容。另加入伪造动作 ID、错误引用、跨用户素材、过期确认、超预算循环和人工接管竞态，证明约束实际阻止了操作。

这些是拟实施协议与验收设计，**本轮未建立运行中的产品 Agent，也未完成真实 API、数据库及浏览器联合验证**。

### 9.3 不可跳过的阶段验收

- G0-S：T01-T04 的软件验证通过。真实模型、模板、资料范围和持久恢复有证据；不通过则不进入大量产品开发。
- G0-P：T37 在物理规则/选证冻结前完成实机规程验证。审核目标、适用条件、通过/不通过/无效标准和安全停止条件；无法安全取得某类样例则记录未验证，不故意制造危险故障。未通过可继续 L1，禁止启用高等级规程结论或承诺 L2。
- G1：P1 完成。真实输入和素材可保存、恢复、隔离；仅浏览器本地状态不通过。
- G2：P2 完成。包含 T41；真实图片、来源、Agent 提案与受控步骤贯通，非法提案被拒绝。没有 G0-P 时只验收明确的 L1 范围。
- G3：P3 完成。反例、必要复测与不可验证出口真正影响后台；模型范围外问题不被“枚举完毕”误当作正常。
- G4：P4 完成。包含 T40；真实接单、续聊、值守时段和无人接单处理均有记录。
- G5：P5、数据准备、G0-P 和运营资源均满足第 11 节放行矩阵，才进入 L2。任一关键反例未通过，相关能力或等级保持关闭。

### 9.4 并行与串行关系

A 先固定权限、会话与事件接口；B 可同时审核资料并完成真实模型试验；C 先建立模板交互和端到端测试框架。接口确定后再并行做各个纵向流程。

迁移、核心状态类型和契约模式必须指定一个负责人合并。不得同时各自建立一套会话状态，也不得让前端以临时假结构长期推进。前端短期测试夹具可以使用，但要有清晰测试标识、对应真实接口任务和删除日期。

每例保存输入/素材版本、实际事件与回执、测试者、结果、证据位置和失败原因。软件故障用例在真实 PostgreSQL 与 Worker 上执行；模型故障注入可以模拟限流，但必须另有真实供应商正常请求记录；真实物理结果、合成状态和故障注入分别统计。

**关键不变量实行测试集零失败门槛：** 越权、已确认事件丢失、重复业务建单、无依据结论升级、人工接管被覆盖、预算失控或已撤回危险步骤继续发出，任何一项失败即阻断相关等级。这里的零失败仅指指定测试集，不代表总体零风险。

L1 还须用真实后端完成三个赛题故事和至少一条失败交接；每个故事的预期终态事先固定，不能把正常可完成故事全部转人工来通过。L2 须 12 条完整故事达到各自预定终态，全部适用异常通过，并完成 G0-P、真实样本与一致恢复。

感知功能在 G0 后、运行保留集前冻结启用字段和阈值。候选初值：每个拟启用视觉字段至少 20 条可判定的独立来源记录，精确率不低于 90%、召回率不低于 70%；模糊/不可见负向必测例不得输出为已证实事实。以上是待审核的试用治理阈值，不是行业标准或已取得成绩；若缺样本或未批准阈值，只保留候选和人工核对，不能宣称该感知能力通过验收。不得看到保留集成绩后再降低门槛。

### 11.3 数据集与指标

先准备不少于 30 条审核的结构化过程用例、20 条图文保留样例和 12 条完整服务故事，作为工程回归起点。这些数量是最低开发覆盖目标，不足以证明总体维修有效率。

开发集与保留集按会话、设备和原始图片来源划分，避免相同素材变体泄漏。真实产品样本、人工构造样本和模拟物理结果分别标记，不能混在一个“成功率”里。

真实图文样本不足时阻断对应识别能力验收；不能用生成图片补齐后声称完成实机识别验证。实机试验由独立记录者记录实际执行和结果，用户对话内容不是唯一真值。

指标包括错误结案率与其分母、结案覆盖率、错误品类路由、无依据动作、实际取证时间、重复步骤、人工接手后的补问量、任务恢复率和每会话模型成本。全部转人工不能算“零错误且效果优秀”。

工程阶段比较相同模型与资料的检索客服、带必要复测的审核固定流程、具有状态维护但不做反例选证的工作流。科研扩展另增加共享同一状态/观察模型和工具预算的主动判定基线，防止把额外模型知识误当选证收益；没有完成该比较时不主张主动策略优于现有方法。

预先冻结三类可失败假设：证据更新是否在相近服务覆盖率下减少无依据结案；反例选证是否在同等允许检查下减少实际取证负担；第二产品是否无需修改核心验效代码且不会增加无依据放行。若固定必要复测同样可靠且更省事，就关闭复杂主动排序。第二产品试验是 L2 之后的研究扩展，不阻塞单产品试用，也不得提前声称跨品类零代码。

“无依据升级率”以实际发布相应等级结论的会话为分母；同时报告全部纳入会话的结案覆盖、待核实、人工转交和放弃比例。物理真值未知样本单列，不能偷偷删掉；没有真实结论真值就不计算真实维修成功率。取证时间报告所有入组用户和各终态分层结果，不只选择已成功修复的人。小样本结果仅作工程观察，不作显著优越或总体安全保证。

### 11.4 端到端等待、队列隔离与性能目标

先以单组织、10 个同时活跃会话测试，记录服务器、供应商、图像大小与网络。保留写入确认 P95 <1 秒、状态查询 P95 <500 毫秒作为候选目标，但它们不代表用户已获得有效下一步。

同一队列系统中区分 `interactive` 与 `ingest`：交互保留独立 Worker/并发额度，离线导入不占满全部交互槽位；共用同一个项目和 PostgreSQL，不因此引入另一套任务平台。L1 没有在线导入时可直接暂停导入 Worker。

从输入被 API 接受开始计时，初始试验配置为：排队最多 30 秒、执行最多 90 秒、总期限最多 120 秒；单次模型调用仍受 45 秒及剩余预算约束。超期限进入明确排队失败/运行失败或人工选项，不无限转圈，原始输入仍保留。这些是控制面和用户网络可达时的待验证目标，不是已经测出的服务能力。

E28 至少覆盖正常模型、慢模型和失联 Worker；长导入与交互同时进行。另记录接受输入到首个有效下一步的 P50/P95、实际完成比例、超时/降级比例、排队长度和模型成本。对正常模型的 10 并发试验至少运行 5 轮，至少 80% 合法正常请求须在总期限内得到预期有效下一步，不能把全量超时或全部转人工视为通过。该 80% 为初始受控试用目标，G0 后可在保留测试前提高，但不是生产 SLO。

未达到上述候选门槛时调整并发、容量或缩减邀请规模，再运行固定测试；不以改分母或屏蔽失败记录替代处理。合成逻辑耗时不能作为整体响应速度。

## 12. 安全、部署与运营

### 12.1 安全必做

- 邀请制账号与明确角色；首版不开放无限注册，不沿用示例超级用户口令。
- 保留成熟认证基础并审查浏览器令牌存储；试用版优先受保护 Cookie 会话，配套 CSRF、同源约束、过期与注销失效，不在日志输出凭证。
- 文件大小、像素数量、实际格式、解码与访问路径校验；普通用户只传允许的图片，管理文档走隔离解析。拒绝可执行内容和任意路径读取。
- 原始素材默认私有，按保留期删除；对外模型只发送完成任务所需的最小内容，预先告知处理范围。默认不将真实素材发送到公共追踪平台。
- 资料导入限制 URL 与跳转，不允许 SSRF；返回 Markdown 做链接、脚本与 HTML 安全处理。
- 模型工具严格白名单；禁任意 SQL、命令、网址访问和自由写业务状态。
- 公网不暴露数据库、调试管理器、开发邮件服务或代理控制台；上线前审查上游 Compose 的默认暴露方式与 Docker socket 挂载权限。
- 配置依赖漏洞与密钥扫描；高风险问题未处理不得进入真实用户试用。开源项目受欢迎不等于没有漏洞。

### 12.2 运行可靠性

应用事务与 outbox 保证本地事件不因投递窗口丢失；队列按至少一次处理设计，业务按幂等执行设计。不能向用户承诺任意远端系统恰好执行一次。

外部写操作必须持有授权及确认记录；对方无幂等能力时使用可回查业务键和人工核对，不在未知结果时盲目重试。人工接管与新的输入优先于旧任务。

知识更新、数据库迁移和应用发布分开：迁移任务由单独受控步骤执行，不让每个 Worker 启动都重复迁移。发布前备份，采用尽量兼容前后版本的迁移；破坏性迁移需独立审批。

### 12.3 一致备份、隔离恢复与部署

本机开发优先 Docker Linux 容器；在线应用与交互 Worker 共用已锁镜像，离线解析可单独镜像。PostgreSQL 与私有文件卷作为同一恢复单元，数据库能启动不等于服务完整恢复。

L2 首版采用可解释的短暂停写方案，不承诺零停机：

1. 进入维护模式，停止接收新的变更与上传完成确认，冻结素材删除；等已开始的提交完成。
2. 停止投递和新任务申领，排空正在提交的 Worker。无法在维护期限内排空则取消本次备份并处理运行，不强杀后直接声称快照一致。
3. 记录备份批次、事件高水位、应用/数据库/契约版本，以及全部被引用素材的存储键、大小和哈希；生成数据库备份并复制同批次素材。
4. 校验完整引用清单与文件，不只抽查几张图；批次标记可恢复后才退出维护模式。
5. 恢复到隔离环境时默认禁止 Worker、外发通知和外部写接口启动，先恢复库和文件，再检查全量引用、版本与未完成运行。
6. 仅在检查通过后重新核对租约/执行代次，将待核对操作保留为待核对，再受控开放 Worker。历史已完成操作不能因恢复重发。

E26 在存在上传、排队和进行中任务时触发，验证维护模式确实拒绝新变更、已确认事件/素材可恢复、孤立素材可清理但不误删，以及外部操作不重放。记录真实恢复时长和备份时间之后可能的数据损失窗口；未演练不填写 RTO/RPO 成绩。

删除与保留期同时覆盖素材、会话中的个人数据、模型请求摘要、流程检查点和备份到期清理。恢复旧备份时先应用删除/撤销清单，避免恢复已经批准删除的用户素材。

目标脚本入口仍为 `doctor.ps1`、`dev-up.ps1`、`verify.ps1`、`backup.ps1`、`restore.ps1`，均尚待开发。生产目标需显式确认；脚本不得自动清空用户数据。

### 12.4 运行观测与成本

最低观测字段：`trace_id`、`case_id`、`event_id`、模型版本、提示版本、知识版本、输入/输出用量、耗时、重试次数、决策原因及错误码。日志默认脱敏，只保存必要的请求摘要和素材引用。

设置每会话、每用户和每日模型预算上限；上限按实际供应商计费与试用预算确定，不写虚构价格。禁止无上限自我反思、多 Agent 循环调用和无限重试。

Langfuse 等平台后续用于观测，不成为业务事实来源；观测系统不可用时，核心服务仍能按受控方式继续。

## 14. 验证阶段启动与最终交付

### 14.1 首个验证阶段的启动顺序

1. 确认赛事允许的复用与开发范围，建立代码来源记录。
2. 固定模板提交，在容器中运行上游基础测试；不先重新设计首页。
3. 用真实模型跑一段描述和一张设备图片，保存有效请求与失败请求记录。
4. 在真实 PostgreSQL 中保存一个会话与一张图片，重启后能恢复。
5. 用两名用户验证资源隔离，再做一次后台任务中断恢复。
6. 完成一份审核服务包草案，确认哪些信息可观察、哪些结论必须保留待验证。

这是 G0 阶段的启动顺序，不要求六件事在第一天全部完成。每日记录已验证环节、未完成条件和实际耗时，阶段成果应当回答“环境与真实链路是否成立”，而不是用页面数量代替验证。

### 14.2 L2 交付包

- 可复现应用源代码、依赖锁文件、容器构建与部署配置。
- 开源来源清单、许可证/NOTICE、实际改动说明与供应链检查结果。
- 版本化产品服务包、知识来源映射、审核记录与撤回方式。
- 自动化测试、真实模型冒烟、双账号闭环、故障恢复与备份恢复记录。
- 保留集定义、对照结果及未通过用例，不删除不利结果。
- 实机试验的条件、观察、结果和不能外推的边界。
- 用户、客服和管理操作说明；明确服务责任人、异常处理及停用方式。
- 当前已实现/未实现/不支持清单；真实业务接口与模拟内容分开。

### 14.3 最终完成判断

第三人不依赖开发者口头说明，能够从干净环境启动系统，用两个账号完成“求助、图片、澄清、指导、反馈、验效、转人工、接单与续聊”，遇到失败知道状态与下一步；开发者能从后台说明每个结果为什么成立，并能恢复一次备份。

满足这一标准，才可以说做出了受限但真实可用的售后系统。物理维修有效性和企业上线资格，分别依据实机试验和企业验收，不由界面完成度代替。
