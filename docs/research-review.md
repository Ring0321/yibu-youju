## 一、先给结论

**方向值得继续，但需要调整创新中心：从“动作之后更新证据”，收紧为“结案之前审查证据能否排除未恢复情形”。**

| 复核问题 | 当前判断 | 依据与边界 |
| --- | --- | --- |
| 场景是否真实 | 有明确业务与产品资料基础 | 赛题要求连续服务，官方 S1 Pro 支持页确有吸力下降排查内容；尚无本团队真实工单统计 |

| 大模型与显式因果模型联合排障 | 2026 年 Frontiers 论文，方法 3.1.2 假设动作无误执行、修复结果观察无不确定性。 [原文](https://www.frontiersin.org/journals/artificial-intelligence/articles/10.3389/frai.2025.1730614/full) | 这是可批判的适用条件，但不能据此声称整个领域都没有解决执行不确定性 |
| 联合建模感知与执行不确定性，并跨任务复用 | PO-PDDL，2026 年预印本，本轮核查正文的模型、规划与局限部分。 [原文](https://arxiv.org/html/2606.15654v2) | 直接否定“把两种不确定性放在一起就是首次创新”的说法；也要将其作为强相关工作 |

**核查后的判断：** 本项目不能靠新增“因果”“POMDP”“多智能体”等术语获得原创性。更可信的路线是：建立针对远程售后结论的可检查机制，找到现有强基线确实处理不好的条件，再用独立实验检验增量。本次检索不是穷尽式系统综述，“未在所查文献中看到完全相同组合”不等于世界首创。

## 三、把科研问题重新定义清楚

### 3.1 从诊断转向结论是否有依据

传统问题是：“设备为什么坏了，下一步修哪里？”

本项目进一步关注：“用户说做了某个步骤之后，已有证据是否足以支持当前服务结论？如果不够，哪项允许执行的观察最有可能改变判断？”

这不是放弃排障，而是在排障与结案之间增加一个有独立责任边界的验效环节。

| 必须分开的事实 | 不能跨越的推断 |
| --- | --- |
| 建议已经发出 | 不等于用户已经执行 |
| 用户报告已经执行 | 不等于完整、正确执行 |
| 照片显示局部外观改善 | 不等于设备功能恢复 |
| 某次功能复测没有复现异常 | 不等于所有故障永久排除 |
| 已生成交接摘要 | 不等于工单已提交，更不等于人工已接单 |

### 3.2 一个真正有辨识度的演示问题

用户提交操作后的照片，某部件外观看起来已经清洁。此时可能同时存在：

- 情形 A：相关状态已经恢复，当前使用正常。
- 情形 B：外观相同，但仍存在未处理的问题，当前使用异常。

如果 A 与 B 对当前照片给出相同解释，系统就没有依据仅凭这张照片判定恢复。再拍一张同样部位、同样信息量的照片，也可能没有帮助。

**系统的差异化表现应当是：能够指出尚未排除的情形、解释为何当前证据不足，并换成有区分作用的复测；无法安全取得该证据时，保留“待验证”。**

这是可演示、可反驳的技术行为，比宣称“更懂情绪”“多智能体更聪明”更具体。

## 四、深化后的三个核心机制

### 4.1 执行不确定性感知的证据状态

将服务记录组织成四种不同对象：用户报告、候选观察、经确认的局部事实、满足限定规程的复测结果。每条记录保存设备归属、原始来源、采集顺序依据、操作关联、适用范围及规则版本。

用户报告完成操作后，系统保留未执行、部分执行、执行成功等尚不能排除的结果，而不是直接把动作的理想效果写成事实。新的观察只能减少与其不相容的候选状态；低质量、无法定位或缺少时序依据的输入保留为候选。

证据有效性不是一个固定过期时间：重新装配可能影响装配状态，却不必令已确认的产品型号失效。按动作影响范围重新审查证据，保留无关事实，避免每轮从头提问。

需要明确：上传时间不能证明拍摄时间；界面中的采集步骤标识也不是现实时间的绝对证明。没有可信采集顺序依据的素材，不升级为操作后的确定证据。图像与该图像的 OCR 结果属于同一来源组；不同来源组也不自动代表统计独立。

### 4.2 反例驱动的结论审查与主动验效

**第一步：明确当前要证明的结论。** 例如“本次限定功能复测通过”，而不是笼统的“设备完全正常”。

**第二步：搜索相容反例。** 在审核过的小规模候选状态中，查找与当前证据一致、但目标结论不成立的状态。反例由结构化模型计算，大模型只负责把其相关差异解释给用户。

**第三步：选择有区分作用的检查。** 对比候选检查在不同状态下可能产生的观察，优先选择能区分相反结果、符合操作前提且负担较低的检查。不能区分结果的重复照片不因“多了一条证据”而获得高分。

**第四步：根据取得的结果重新判断。** 检查未完成、结果模糊或发生新的操作时，继续更新；没有可用检查则停止推断，说明缺少什么依据，并形成交接材料。

工程实现采用单个有状态执行器和独立验效模块，不需要多个大模型相互辩论。模型输出不能自行提升证据等级或绕过结果条件。

### 4.3 带反例审查的可复用验证契约

产品接入不只是上传说明书，而是配置一份“验证契约”：规定哪些结论可以说、什么观察可以支持、什么操作会改变其依据、何时必须交给人工。

| 契约字段 | 作用 |
| --- | --- |
| 产品与版本范围 | 防止型号、地区、固件或资料不匹配 |
| 可输出结论及证据等级 | 区分局部观察、用户反馈、限定复测和业务回执 |
| 动作前提、禁忌与可能影响 | 防止错误指导与操作后沿用过时依据 |
| 观察能力与观察局限 | 指定照片、文字、视频或授权接口究竟能支持哪些事实 |
| 结果条件与未知出口 | 防止没有定义完成标准的流程自动结案 |
| 来源与审核记录 | 使关键规则可回查，不把模型生成规则直接投入使用 |
| 反例测试与回归集 | 检查是否存在“证据满足，但目标仍未达到”的放行路径 |

接入时可进行离线审查：例如某条结案规则只要求“外观已清洁”，审查器返回与之相容但功能仍异常的候选状态，要求补充复测条件或降低结论等级。

**有复用价值的资产是观察与结论的约束机制、审查器和测试规范，不是让一个产品的维修步骤直接套到所有产品上。**

## 五、技术形式化与实现边界

### 5.1 不强行使用虚构概率

首版没有足够的真实执行数据来估计动作成功率和视觉误判率，因此使用有限候选状态集合，而不是填写没有校准依据的 0.8、0.95 等数值。

记当前候选状态为 B_t，动作报告为 a_t，未确定的执行方式为 z。预测状态包含所有仍可能的执行结果：

```text
B_pred = union T(s, a_t, z), for s in B_t and admissible z
B_next = {s in B_pred: s is compatible with applicable observations}
```

这是保守的集合式状态估计，并非本项目新创的理论。观察与动作关系须来自审核模型；模型遗漏或错误会导致推断失真，不能由上述公式自行解决。

### 5.2 结论放行条件

对限定结论 c，形成较高等级结果至少需要同时满足：

```text
候选状态非空
且所有剩余状态均满足限定结论 c
且满足该结论指定的功能复测与时序要求
且未触发范围外、证据冲突、安全或权限阻断
```

候选状态为空意味着证据、模型或设备绑定可能冲突，必须暂停，不能利用“空集合中的所有元素均满足条件”的逻辑漏洞放行。

尚存在模型外故障时，不将排除已知原因等同于排除所有原因。实际结论限定为经过核实的那次观察或复测，不写“永久修复”。

### 5.3 无概率的首版检查排序

将 B 中结论相反的状态配对，形成 P(B)。检查 q 的每种观察 o 对应仍相容的状态集合 B(q,o)。对于不改变设备状态的观察，采用：

```text
score(q) = [|P(B)| - max_o |P(B(q,o))|] / cost(q)
```

含义是：按最不利观察结果估计能够消除多少结论冲突，再除以取证负担。优先选择分数为正且满足前提的检查；没有适用检查则返回待验证。

这是基于已有主动判定思想的首版启发式，不是全局最优策略，不继承已有方法的近似保证。动作会改变状态、观察结果相关或模型不完整时，已有理论条件可能不成立。改变设备状态的检查需要作为动作单独执行、再规划，不能塞进静态检查集合。

首版建议限制在不超过 64 个候选状态、8 项候选检查；超限时进入人工或显式降级路径，不静默删除不利状态。实际参数需要按服务包规模测试。当前小实验只使用 8 个合成状态，没有验证上述规模的端到端性能。

### 5.4 大模型具体负责什么

大模型负责自然语言与图片中的产品、症状、用户约束和局部观察候选；检索模块按已确认产品与资料范围提供依据；执行器负责前提、证据适用性、状态和权限；验效模块返回结论等级与尚未排除的情形；模型再据此生成用户可理解的解释。

严格区分候选与事实不意味着退化成按钮客服。AI 的价值在于将开放表达、不同拍摄方式与非标准反馈映射到同一服务状态，并针对具体证据缺口组织下一轮交流。必须通过含自由描述和图片的对照实验验证这一增量。

## 六、真实产品资料能支持到哪一步

eufy 官方 S1 Pro 吸力下降支持页列出两组排查方向：进尘路径相关部位的残留物，以及护条、尘盒出口密封等部位的损坏或缺失；仍有问题时联系支持。该页面没有给出可直接用于本项目的客观吸力恢复阈值，也没有证明本团队能够调用设备遥测接口。 [官方支持页](https://service.eufy.com/article-description/What-should-I-do-if-my-S1-Pro-s-suction-becomes-weak)

因此首版限定为：**两个有文档依据的排查方向＋未覆盖/无法确认出口**。不把电机诊断、自动保修判定或其他自行推测的故障分支加入真实产品事实。

| 能力 | 现在的可落地判断 | 放行条件或降级方案 |
| --- | --- | --- |
| 产品歧义澄清 | 可做 | 目录、型号标识和用户确认；识别不稳则保留候选 |
| 图片提取局部观察 | 可做候选识别 | 需要真实图片验证，不宣称能发现所有细微损坏 |
| 按官方资料组织排障 | 可做受限流程 | 具体清洁、装配和操作禁忌仍须完整手册与人工审核 |
| 动作后审查证据、找逻辑反例 | 小规模计算可做 | 效果依赖状态、动作及观察模型的正确性 |
| 自动确认真实吸力恢复 | 当前不可承诺 | 缺少审核后的可观测复测规程与真实采集数据 |
| 记录用户确认恢复 | 可做 | 明确标注为用户反馈，不改写为仪器检测结果 |
| 真实客服交接和质保处理 | 接口权限未确认 | 首版生成草稿，模拟回执明显标注，不自动作最终业务决定 |

功能验效规程必须由具备产品知识的人确认可操作性与安全性，至少明确使用条件、观察目标、通过标准、失败标准和不确定出口。即便后来采用清扫结果评估，也只能证明该条件下的清扫表现，不能把它直接换算成吸力数值。

如果没有实机：演示理解、指导、状态维护、反例检查和交接流程；物理执行与功能结果显式使用模拟场景。若有实机但无合格复测条件：展示真实操作和用户反馈，不显示“系统已客观证实修复”。

## 七、本轮已经完成的机制核验

### 7.1 实验性质

已编写并在本机运行一个 Python 标准库小实验。它不是产品原型，不调用模型、不识别真实照片、不连接硬件，也不承载真实用户信息。

合成设备有三个布尔属性：外观条件、装配条件、其他条件，共 8 个状态。程序人为定义三者均满足时功能为真。该定义用于测试推理行为，不是对 S1 Pro 物理结构、故障概率或维修效果的建模。

### 7.2 实际结果

**20 项单元测试通过；其中一项枚举了 8 个状态构成的全部 255 个非空候选集合。** 255 个集合不是 255 次独立维修实验，也不能与 20 项测试相加为样本量。

| 测试内容 | 已观察结果 |
| --- | --- |
| 只有外观改善证据 | 剩余 4 个候选状态，其中有 3 个不满足合成功能条件，不放行 |
| 用户报告已执行动作 | 保留未执行、部分或完整执行可能，不直接写入理想效果 |
| 动作只影响部分条件 | 仅相关旧证据失效；型号等无关信息保留 |
| 操作后重新上传操作前素材 | 按已有采集顺序标注拒绝作为新状态依据；不声称能够自动识破伪造的拍摄时间 |
| 拍摄顺序不明、设备不符、未来序号 | 不当作当前可用事实 |
| 图片及其 OCR | 按同一来源组记录，不将两者重复累计成两份独立证据 |
| 模型候选或用户自述功能正常 | 不升级为经过客观复测的结果 |
| 矛盾证据使候选集合为空 | 返回冲突，不误用空集逻辑判定成功 |
| 全部局部属性看似满足 | 仍要求限定功能复测条件，局部观察不替代验效契约 |
| 外观相同但结果相反 | 选择能区分两者的合成功能测试，不选择重复外观照片 |
| 功能测试不可获得，其他检查无信息 | 返回无适用检查，不继续无意义索取素材 |
| 噪声观察的两种结果都可能出现 | 不把其当作确定的区分手段 |
| 检查会改变状态 | 不作为静态无副作用观察使用 |
| 同一事件重复到达 | 幂等处理；冲突事件标识被拒绝 |
| 离线审查外观条件即结案的规则 | 找到 3 个合成反例，要求补充条件 |

原始测试入口为工作区 `work/research_v6/test_verification_probe.py`；机制实现为同目录 `verification_probe.py`。运行方式：`rtk proxy python -m unittest discover -s work/research_v6 -p test_verification_probe.py -v`。

测试只能说明这些人工构造条件下的程序行为符合预期。`fixture_verified` 是测试夹具提供正确观察的假设，不是现实模型达到这一等级的证明。生产系统必须由受控适配器决定证据等级，不能信任客户端或大模型自报字段。

### 7.3 尚未验证

真实图片识别、真实动作识别、产品事实完整性、复测规程正确性、用户耗时、用户信任、真实误结案率、跨产品迁移成本、服务接口可靠性均未完成验证。没有依据填写改善百分比、维修成功率、商业节省金额或上线状态。

## 八、怎样验证它真的比已有方法好

### 8.1 三个可被否定的假设

| 假设 | 要求观察到的增量 | 何时判定不成立 |
| --- | --- | --- |
| H1：执行不确定性与证据适用性联动能减少错误结论 | 在部分执行、错误时序和相关证据场景中优于有记忆的规则基线 | 只在故意删掉基础校验的弱基线上提升，或实际来自更保守地全部转人工 |
| H2：反例驱动选证能降低用户负担 | 在相近错误风险与服务覆盖率下减少取证时间或无效检查 | 固定的短复测流程一样好或更好；复杂选择没有实际收益 |
| H3：验证契约能降低产品接入错误 | 保持核心引擎不变时，新服务包的无依据放行路径更少且审核成本可接受 | 需要持续修改核心规则，或节省的配置成本被大量人工建模抵消 |

### 8.2 基线必须足够强

1. 相同模型与资料的检索增强客服，加标准化“是否恢复”追问。
2. 经人工审核的固定决策树，带必要的功能复测、未知出口和时序检查。
3. 状态感知的声明式工作流，具有证据失效、结果等级和执行反馈，但不做反例驱动选证。
4. 同一状态与观察模型下的主动判定或信念规划基线，具有相同的工具、检查候选与预算。
5. 完整方案及去掉执行不确定性、去掉来源与时序约束、固定检查顺序的消融版本。

只与“没有复测、没有状态、没有拒答能力”的聊天机器人比较，无法证明核心贡献。所有版本使用相同的产品资料、模型权限与动作安全限制；额外知识和更好的提示词不能只提供给完整方案。

### 8.3 分层而非混合评价

| 层次 | 输入和真值 | 回答的问题 |
| --- | --- | --- |
| 机制层 | 人工审核的结构化事件和独立设计的反例 | 验效规则、状态更新、选证是否按定义工作 |
| 感知层 | 真实图片与自由描述，独立标注可见事实和不可见事实 | AI 会不会把看不见的条件当作已知 |
| 闭环层 | 真实用户执行与独立人员记录的实际结果 | 误执行、理解偏差与额外取证负担是否改变整体收益 |

同一个大模型生成场景、回答场景并裁判场景，会形成循环论证。合成集需要人工复核与独立保留集；实机最终状态由独立观察或经认可的仪器/规程标注，不由客服对话自评分替代。

### 8.4 指标和实验设计

- 错误结案率：被系统输出为较高等级完成、但独立结果不满足对应条件的会话数，除以该等级结案数；分母为零时记为不可计算。
- 结案覆盖率：该等级结案数除以全部符合范围的会话数。与错误结案率同时报告，避免用全部拒绝换取表面零错误。
- 用户负担：分别记录真实操作时间、主动取证次数、重复步骤及放弃率，不只用对话轮数替代。
- 无效取证比例：未改变任何相关结果判定、也未满足必要契约条件的取证，需独立复核定义。
- 安全与范围外行为：不适用操作、超出权限、过早保证、未知故障被强制归入已知原因的发生次数。
- 接入成本：资料整理、审核、配置、接口与回归所花工时，以及核心引擎改动量。

24 小时阶段安排不少于 12 条关键演示/异常回放，仅作为烟雾测试。后续先以小规模真实用户与设备试验估计难度和方差，再确定正式样本量；同一用户、设备和会话内多张图片不能当作独立样本扩大统计量。

报告置信区间与用户/设备聚类影响；没有预先确定的非劣效界限、足够样本量和检验设计时，不能宣称“在相同风险下显著降低成本”。模型、规则和检查成本在保留集评价前冻结。

最重要的可失败检验：**如果一项低成本、始终可执行的固定功能复测已经足够，复杂主动规划可能没有必要。** 此时应保留结论审查与状态治理，把检查选择降为简单规则，不为维持科研叙事制造复杂性。

## 九、24 小时落地版本

### 9.1 资源假设

按约 3 人并行协作、可使用多模态模型接口、公开资料可取得进行估计。团队实际能力、S1 Pro 实机、售后专业审核人、真实工单和业务接口尚未确认，因此不能把这一估计写成保证。

### 9.2 原型边界

必做：一个设备类别确认入口、一个 S1 Pro 吸力下降服务包、两个文档支持的方向、一个未知出口、图片候选输入、动作记录、反例审查、分级结果和交接草稿。

演示页面只展示三类核心内容：用户输入与单步任务、当前结论及缺失依据、服务记录与交接状态。研究人员查看的候选状态和来源链放在展开区域，不要求普通用户理解术语。

不做：基础模型训练、实时视频/AR、自动电气维修、全品类诊断、自动退款换货、自动质保最终决定、无授权订单或设备接口、未经验证的自动学习上线。

### 9.3 工程构成

前端采用图片与文字输入、步骤反馈、暂停恢复和结果等级展示。后端使用结构化接口、轻量关系存储及事件表；原始素材与解析候选分开存储。知识检索先匹配产品与版本，再进行关键词和语义召回、重排与来源校验。对小规模审核资料集，不必为了架构复杂度部署大型图数据库。

编排器使用显式状态机；验效模块采用有限状态枚举；服务契约采用有模式校验的配置。接口返回结构化的 `result_grade`、`remaining_counterexample`、`next_check`、`blocking_reason` 和 `evidence_refs`。上述是拟设计接口，不是已经联调的真实业务服务。

模型调用失败时回到已审核的固定流程；模型输出格式不合规时不更新关键状态；不确定的细微图像观察提示重新取证或交人工。检索资料中的指令文本不能改变系统权限或执行流程。

| 时间 | 优先工作 | 验收对象 |
| --- | --- | --- |
| 0 至 4 小时 | 资料审查、明确两类方向、结论等级和禁忌；建立契约与状态模型 | 无来源规则、不可观察条件及自动放行缺口清单 |
| 4 至 10 小时 | 单页交互、结构化理解、证据与动作事件；同时实现验效模块 | 用户输入能进入正确产品路径，模型候选不直接改写事实 |
| 10 至 16 小时 | 反例解释、可用检查选择、操作后更新、结果与交接 | 一条正常路径及一条部分执行/旧证据路径闭环 |
| 16 至 20 小时 | 异常、不可观察、无法执行、断点恢复和幂等测试 | 待验证与已恢复、草稿与真实回执不混淆 |
| 20 至 24 小时 | 对照演示、记录实测、修正表述并冻结 | 成功与失败路径均可重现，模拟内容醒目标注 |

如果 4 小时内仍无法确认物理复测规程，自动验效仅使用明确标注的模拟观察；真实服务路径保留用户反馈与人工核查。如果 16 小时仍无法稳定解析图片，保留图片上传和人工确认，不虚构识别结果。

## 十、复用价值如何兑现

系统面向三种接入方式：独立售后页面、现有客服系统的验效接口、人工客服的取证与交接辅助。当前只确定共同的数据与决策边界，不宣称已兼容任何企业平台。

| 可复用部分 | 每个产品必须重新做的部分 |
| --- | --- |
| 证据、动作与结论的统一结构 | 产品型号、部件与可见特征 |
| 时序与来源审查、反例搜索 | 真实动作效果、禁忌与观察能力 |
| 检查选择与结果等级 | 安全有效的功能复测规程 |
| 事件恢复、交接和评价程序 | 业务系统的权限、接口与字段 |
| 契约审查与回归测试框架 | 真实样本采集和产品专业审核 |

第二产品不是再复制一段提示词。接入时记录新配置、必要适配器、全部人工审核工时与回归结果；核心引擎是否保持不变作为可核查的复用证据。不同产品的安全规程和功能标准不能共用。

不建议首版把吸奶器等具有不同身体接触与使用安全要求的产品作为自动故障处理扩展。可用于型号歧义澄清，但跨品类真实排障须单独专业审核。

## 十一、与上一版相比，明确改什么

| v5 表述 | v6 处理 |
| --- | --- |
| 动作影响驱动的动态证据推理作为第一创新 | 保留为技术基础；创新主线改为服务结论可辨识性与反例驱动验效 |
| 缺失条件补齐和低成本复测 | 强化为区分相反结果的观察选择；明确“覆盖条件”不等于验证成功 |

| 吸力下降若干分支 | 限定到官方支持的两组方向与未知出口 |
| 可观察结果满足即确认 | 加入功能复测条件、执行不确定性与模型范围限制 |
| 工程方案与待验证效果 | 补充已运行的有限逻辑核验，继续明确真实效果未测 |

## 十二、推荐的研究与参赛定位

**当前适合主张：** 面向远程售后，提出结论导向的反例审查、主动验效和契约化接入机制，并形成可复现的受限系统原型。

**经过后续实证才可主张：** 在执行偏差、证据时效变化与观察受限的条件下，相比强状态基线降低错误结案或用户取证成本，并保持可接受的服务覆盖率。

**目前不能主张：** 首创不确定性规划、首创因果售后、真实维修成功率提升、跨品类零成本迁移、正式安全保证或已达到论文录用水平。

如果继续向科研成果推进，优先沉淀三项可检查产物：带执行偏差和证据时效标注的相容反例案例集；支持结论等级与观察局限的验证契约及审查程序；相同模型、知识和权限条件下的强基线对照结果。只有出现不能由基础时序校验、额外知识或更高拒绝率解释的稳定增量，才进一步讨论独立方法论文。当前不把这个有限检查排序公式命名为新的算法成果。

最终建议是保留业务题目，改变研究落点：**真正有价值的不是让系统总能给出一个“已解决”，而是让它知道什么依据足以支持哪种结论，主动补齐有用证据，并把确实无法验证的部分完整交出去。**
