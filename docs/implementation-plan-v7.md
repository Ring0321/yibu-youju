# 一步有据：详细开发计划与开源复用方案

> 版本：v7 | 制定日期：2026-09-22 | 文档性质：可执行开发计划，不是已完成产品说明。
>
> 目标：做出真实运行、可持续保存、能处理异常、有人接续处理的售后服务系统。验收对象是服务过程和后台事实，不是页面数量。

## 0. 执行摘要

**确定路线：以成熟全栈工程为基础，接入真实模型和审核知识，开发独立的服务状态、反例审查与验效内核，并配套可实际接单的人工工作台。**

工程采用模块化单体，首版单组织运行，不做多个独立微服务。业务接口和后台任务共用代码与数据库；用户端、客服端、知识审核端共享权限体系。前端不计算结案结果、不伪造业务回执。

| 决策 | 本计划确定的做法 |
| --- | --- |
| 工程基础 | 复用 FastAPI 官方全栈模板的前后端工程、数据库迁移、登录基础、接口客户端和测试结构 |
| 流程执行 | 复用 LangGraph 的有状态流程与持久化能力；业务事实以应用数据库为准 |
| 知识检索 | PostgreSQL + pgvector；产品、地区、版本和有效状态先过滤，再召回与排序 |
| 资料解析 | Docling 离线导入；审核后才发布，不让实时问答请求承担文档解析 |
| 后台任务 | 采用 PostgreSQL 任务队列 Procrastinate，承担模型、导入和可重试处理；先完成兼容与崩溃恢复验证 |
| 核心自研 | 产品验证契约、证据适用性、动作影响更新、相容反例、复测选择、结论等级 |
| 人工闭环 | 首版内置精简真实工作台；后续按需要接企业系统或 Chatwoot，而不是首版同时部署另一套平台 |
| 测试方式 | 逻辑单测 + 真实数据库集成 + 真实模型冒烟 + 双用户端到端 + 故障恢复与实机验证 |
| 完成标准 | 任何“已保存、已识别、已提交、已接单、已验证”都有可回查的真实记录 |

**工期判断：** 24 小时适合单场景受限运行版；达到小范围真实试用，按约 3 人、11 至 15 个有效工作日规划，且模型账号、资料、审核人和设备条件到位。工时是估算，不是交付保证。企业正式上线另设审批与试运行，不拿赛场验收代替生产验收。

## 2. “真实可用”的定义

### 2.1 必须跑通的完整过程

1. 真实用户登录或获得受控访问身份，创建属于自己的服务会话。
2. 提交自由描述和真实图片，文件实际存储，上传失败有明确提示。
3. 后台调用真实模型，记录调用状态与版本，提取产品和症状候选；识别不了时允许用户纠正。
4. 系统确认产品后检索适用且已审核的资料，指导内容可定位到来源。
5. 用户执行一个适用步骤，报告完成、未完成、部分完成或无法执行。
6. 后台记录操作，更新相关证据与候选状态，不靠前端变量假装状态变化。
7. 验效模块判断当前结论能否成立；必要时选择复测，无法验证时保留待验证。
8. 需要人工时实际创建内部服务单，客服用另一个账号看到、接单、补问并处理。
9. 用户能看到真实处理进展；刷新页面、重新登录或服务重启后不会丢失已提交内容。
10. 全程的来源、状态、模型调用、人工操作和结论等级可回查。

### 2.2 三个交付等级

| 等级 | 用途 | 可以承诺 | 不可以承诺 |
| --- | --- | --- | --- |
| L1：受限运行版 | 赛场与受控体验 | 真实模型、真实资料、真实数据库和内部人工接单；单型号故障族 | 自动证明物理修复、全品类支持、企业正式质保处理 |
| L2：小范围试用版 | 邀请真实用户使用 | 完成权限、恢复、导入审核、隐私处理、测试和受控实机验证 | 未经组织授权的官方售后身份与企业生产保证 |
| L3：企业上线版 | 企业真实业务 | 经授权接口、正式运营责任、监控和安全验收下的服务 | 由开发团队自行宣告通过企业验收 |

**没有实机并不妨碍建立真实软件服务，但不能据此宣称物理维修效果已验证。没有企业接口也不妨碍内部真实接单，但必须写明“项目客服”，不能冒充 Anker 官方客服。**

| 命题要求 | 可操作实现 | 验收证据 | 首版边界 |
| --- | --- | --- | --- |
| 理解文本、情绪与紧迫性 | 提取用户明确表达的焦急、使用期限、操作限制，调整单步信息量 | 原始描述、提取字段、可纠正入口、后续路径 | 不从一张人脸图推断心理状态；情绪不改变安全与质保标准 |
| 多模态理解 | 产品外观、铭牌、报错界面和局部状态的候选提取 | 真实模型请求记录、素材引用、识别失败样本 | 不把不可见内部状态当作已知 |
| 产品消歧 | 产品目录、别名、图文候选与用户确认 | “S1 Pro 不吸了”必须先确认类别 | 吸奶器只支持类别澄清与转交，不直接套用扫地机流程 |
| 技术知识库 | 已审核文档分块、产品过滤、检索与来源定位 | 引用能回到原始段落及有效版本 | 原始网页和模型生成规则不能自动发布 |
| 历史工单 | 授权范围内检索同一用户或经脱敏批准的案例 | 权限测试、访问记录、引用的历史案例 | 不能暗示已获得 Anker 私有工单 |
| 故障定位与指导 | 两类有官方依据的排查方向，逐步执行 | 每一步有来源、前提和反馈，未知有出口 | 不自行新增电机故障等无依据分支 |
| 服务闭环 | 结果等级、内部真实工单、人工接续 | 双账号真实接单与用户端同步 | 内部回执不等同于企业系统回执 |
| 渠道与质保 | 记录购买渠道、凭证和查询状态，人工核对 | 未找到订单不会自动判为不保修 | 无授权接口时明确“尚未核验”，不返回假查询结果 |
| 流程与规则结合 | 受控工作流调用独立验效内核 | 非法跳步、证据不足和重复请求测试 | 模型不得直接修改权限或最终业务状态 |
| 创新与复用 | 相容反例、有效复测、验证契约 | 反例用例、强基线对照、第二产品适配记录 | 既有框架能力不宣称为自研算法 |

### 4.3 复用接入必须遵循的流程

1. 记录仓库 URL、完整提交 SHA、许可证和所用目录；在独立分支导入模板，不覆盖既有研究文件。
2. 查看安装脚本、容器构建、默认账号、遥测和自动部署配置；不直接运行来源不明的一键部署脚本。
3. 保留 LICENSE、必要 NOTICE 和第三方来源说明；不得将上游界面及核心能力整体署名为自主研发。
4. 上游模板示例 `.env` 只做字段参考，真实密钥只进入未提交的本地配置或受控密钥系统。
5. 先运行上游基础测试，再加入依赖与新业务；每次升级都重新验证迁移、权限、恢复与关键流程。
6. 固定 Python/Bun 依赖锁及容器镜像摘要。下文 SHA 是调研快照，不等于所有主分支提交都适合直接用于生产。

### 4.4 已发现的兼容与恢复风险

模板抽查提交的后端要求 `Python >=3.14`，镜像采用 Python 3.14，前端构建采用 Bun；前端清单已有 Playwright `1.62.1`。保留模板的构建方式，不同时引入另一种包管理器。 [后端清单](https://github.com/fastapi/full-stack-fastapi-template/blob/cb740b656d7a0a6c5e12c7bf8e50343ec94ee9c7/backend/pyproject.toml)、[构建文件](https://github.com/fastapi/full-stack-fastapi-template/blob/cb740b656d7a0a6c5e12c7bf8e50343ec94ee9c7/backend/Dockerfile)、[前端清单](https://github.com/fastapi/full-stack-fastapi-template/blob/cb740b656d7a0a6c5e12c7bf8e50343ec94ee9c7/frontend/package.json)

LangGraph 抽查源码标注核心包 `1.2.12`、PostgreSQL 检查点包 `3.1.2`；这些是源码声明，发布可用性和依赖组合仍须在 D0 验证后锁定。恢复时节点可能从头执行，检查点不等于外部操作恰好执行一次。 [中断文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

任务队列也不能默认“进程被杀后会自动安全重跑”。Procrastinate 文档明确需要处理失联任务；本项目必须实现心跳检查、有限重试与业务幂等。 [失联任务处理](https://procrastinate.readthedocs.io/en/stable/howto/production/retry_stalled_jobs.html)

## 5. 系统架构与职责

### 5.1 部署组成

| 组成 | 内容 | 首版部署方式 |
| --- | --- | --- |
| Web | 用户服务、客服工作台、知识审核 | React 构建产物随应用部署，同源访问 |
| API | 身份、会话、素材、状态、人工服务、知识管理 | FastAPI 应用进程 |
| Worker | 模型调用、流程执行、资料解析、任务恢复 | 同一代码库的独立后台进程 |
| 数据库 | 业务记录、事件、向量、任务、检查点 | 一个 PostgreSQL 实例，表或 schema 明确划分 |
| 素材存储 | 图片和文档原件 | 首版专用持久卷，数据库存元数据；多实例前迁至私有对象存储 |
| 入口 | HTTPS、请求大小和基本访问限制 | 受控反向代理；数据库与管理端口不暴露公网 |

L1 不部署 Kubernetes、Kafka、独立图数据库、额外向量库或多个 Agent 平台。离线解析可单独构建镜像，避免重型解析依赖进入在线问答容器。

### 5.2 四条责任边界

1. **模型理解，不做最终业务提交。** 可以提出产品候选、局部观察与建议表达；不能设置证据可信等级、审批结果或已接单状态。
2. **数据库保存事实。** 所有用户提交、人工确认与状态变更先成为可持久化事件；检查点不是另一份拥有最终解释权的业务数据库。
3. **验效模块决定结论等级。** 只接受符合模式、来源和权限要求的输入，返回结构化结果及不足依据。
4. **业务适配器执行外部动作。** 订单、工单和通知经授权、幂等与回执检查，不由大模型拼接 URL 任意调用。

### 5.3 一次真实请求的时序

1. API 校验身份、会话归属、文件归属与 `expected_version`，检查 `Idempotency-Key`。
2. 在同一个数据库事务中写入用户事件、更新会话版本并写 outbox；返回真实 `event_id` 和 `run_id`。
3. outbox 投递后台任务，重复投递允许发生，但 `run_id` 与步骤执行记录必须去重。
4. Worker 读取当前版本，调用模型或检索；网络等待期间不持有长时间业务行锁。
5. 输出先经模式与权限校验；若会话版本已被用户新输入或客服接管改变，旧结果不得覆盖新状态。
6. 验效模块运行，事务性保存决策、证据引用和下一个允许操作；更新任务状态。
7. 前端通过受鉴权的事件流或轮询获取后端状态；断线后按事件序号补取，不重复触发模型调用。

检查点保存 `case_id`、输入事件、步骤位置及相关版本，业务事件保存事实。两者写入不能假定天然跨事务原子；每个节点通过幂等业务服务读取或取得已保存结果，重放时先核对业务版本和步骤记录。

## 6. 数据模型与状态规则

### 6.1 核心数据表

| 表/对象 | 关键字段 | 作用 |
| --- | --- | --- |
| `users` / `memberships` | 身份、角色、组织、禁用状态 | 用户、客服、知识审核员和管理员权限 |
| `products` / `product_aliases` | 品类、型号、别名、地区、适用版本 | 消歧与资料范围 |
| `service_cases` | 所有人、产品、流程状态、版本、契约版本、当前负责人 | 售后会话主记录 |
| `case_events` | 会话、顺序号、事件类型、操作者、输入版本、幂等键 | 业务历史与状态重放 |
| `assets` | 所有人、存储键、哈希、格式、大小、上传状态、声明拍摄时间 | 原始文件与访问控制 |
| `observations` | 素材引用、谓词、值、来源类型、候选/确认状态、确认人 | 区分模型推断和已核实记录 |
| `actions` / `action_reports` | 动作实例、前提、影响范围、用户报告、实际时序 | 区分建议发出与执行反馈 |
| `documents` / `document_versions` / `chunks` | 来源、内容哈希、版本、适用范围、审核状态、定位、向量 | 可回查且可回滚的知识 |
| `service_packs` / `pack_versions` | 状态模型、动作、观察能力、结果条件、批准人 | 可执行验证契约 |
| `decisions` / `verification_records` | 输入版本、剩余反例、检查、依据、结果等级 | 可解释验效记录 |
| `service_tickets` / `ticket_events` | 内部单号、状态、接单人、消息、业务回执 | 真实人工处理闭环 |
| `model_runs` / `step_runs` | 请求引用、模型/提示版本、用量、耗时、状态、重试 | 诊断、成本和幂等结果缓存 |
| `outbox` / `integration_receipts` | 操作键、适配器、投递次数、远端单号、回执状态 | 跨系统一致性与异常补偿 |

派生的会话快照可以重建；原始事实采用追加更正事件，不偷偷覆盖历史。审计记录本身不是防篡改证明，数据库管理员仍有能力修改数据；正式审计要求另行设计。

### 6.2 必须建立的约束

- 同一会话事件序号唯一；同一幂等键重复提交相同请求返回已有结果，不同内容返回冲突。
- 所有会话、素材、工单查询先做组织与所有权检查；不能只凭随机 ID 难猜测来保护数据。
- 用户端不能提交 `trusted=true`、`verified=true`、任意 `role` 或最终结案状态。
- 动作反馈必须绑定具体动作实例，不能把上一轮“做完了”归到新动作。
- 模型输出必须带 `input_case_version`；过期结果保留为历史，不应用到当前状态。
- 同一照片与其 OCR 是一个来源组；不同图片也不自动按统计独立处理。
- 没有可靠拍摄顺序依据时标注未知；上传时间、EXIF、任务口令均不单独证明照片真实性。

### 6.3 流程状态与结果等级分开

流程状态建议为 `INTAKE`、`NEEDS_PRODUCT_CONFIRMATION`、`TRIAGING`、`WAITING_USER_ACTION`、`WAITING_VERIFICATION`、`HUMAN_QUEUE`、`HUMAN_ACTIVE`、`CLOSED`。

结果类型另存：`PENDING`、`USER_REPORTED_RECOVERY`、`LOCAL_OBSERVATION_ONLY`、`PROTOCOL_RESULT_SUPPORTED`、`UNRESOLVED`、`OUT_OF_SCOPE`、`EVIDENCE_CONFLICT`。关闭会话不代表修复成功，关闭原因必须单独记录。

`PROTOCOL_RESULT_SUPPORTED` 仅代表在指定规程、环境和证据范围内得到支持，不能翻译成“设备完全正常”。未建立真实复测规程时关闭该结果类型的自动进入路径。

人工接单使用独立事件与身份记录。分配给某客服不代表客服已经接受处理，必须有真实接单动作。

## 7. 核心模块如何实现

### 7.1 多模态理解与模型适配

定义一个模型接口，统一文字、图片、结构化结果、超时和用量记录。先接一个具备图片理解与结构化输出能力的真实供应商；模型名称根据实际账号权限确定，不在未验证时写死某个“最新最强”型号。

结构化输出包括 `product_candidates`、`symptoms`、`reported_actions`、`visible_observations`、`user_constraints`、`urgency_cues`、`missing_information`。每项带原文或素材引用，不允许无来源字段悄悄进入当前事实。

不训练基础模型。先用 20 至 30 条图文样例筛查适用性，再制作开发集与独立保留集。图片拒识、模糊、不可见以及产品不匹配必须是正常输出。

每轮最多一次理解调用和一次必要表达调用，优先一次结构化理解加确定性渲染；格式错误最多修复一次。超时、限流、预算不足时降级到审核步骤或人工，不展示编造的模型分析。

### 7.2 知识导入与检索

导入路径：人工批准的 URL/文件 → 解析 → 来源与产品元数据 → 分块 → 审核 → 嵌入 → 发布版本。

先限定官方支持资料和用户授权文档，不运行开放网页自动搜答案。图片、PDF 和网页内容不被视为可执行系统指令。管理端链接抓取禁止访问本机、内网和云元数据地址，并重新检查跳转目标。

分块保留完整动作、注意事项与前提，不能将“不要执行”与后面的动作拆开后单独召回。每块有标题路径、段落/页码、原始 URL、内容哈希和版本。

检索先按产品、品类、地区、固件/资料适用版本和发布状态过滤，再组合型号/错误码匹配与向量召回。中文查询不能直接假定英文全文检索配置有效；首版用明确别名和型号匹配配合多语嵌入，必要时经对照后增加中文分词检索。

小知识库优先精确向量扫描，达到数据规模与延迟要求后再配置近似索引。切换嵌入模型时新建对应版本索引，禁止混用不同向量维度或语义空间。

检索片段用于解释与受控规则选择，不允许模型临时创造维修操作。引用验证器检查来源 ID 存在、适用且为当前准许版本；无适用来源时进入未知出口。

### 7.3 验证契约与发布

每个服务包至少包含产品范围、状态谓词、允许动作、动作前提、影响集合、可能执行结果、观察能力、结果类型、功能复测规程、禁止动作和未知出口。

采用模式校验的 JSON/YAML，禁止嵌入任意代码或使用 `eval`。包发布需审核人批准、记录版本、执行反例测试。正在进行的会话固定契约版本；遇到安全撤回时立即阻止相关操作并转人工，而非静默沿用旧危险规则。

模型可以协助提出规则草稿，但“来自说明书”不等于“模型提取无误”，必须逐条检查动作、否定表达、条件与来源。

### 7.4 自研验效内核

输入是已确认产品、契约版本、事件、观察和允许检查；输出为剩余候选状态、尚未排除的反例、可用检查、阻断原因和结果等级。

实现顺序：

1. 将现有合成模块改成可传入领域配置的纯函数；保留原测试，但取消写死的产品与功能定义。
2. 对“未执行、部分执行、正确执行、执行结果未知”分别定义允许结果，不自动应用理想动作效果。
3. 依据动作影响重审证据；保留不受影响事实。一个结论有多个有效支持时不因撤销一条就必然变假。
4. 搜索与当前有效观察相容、但目标结论不成立的状态；有反例就不得输出该高等级结论。
5. 从安全且当前可执行的检查中选择有区分能力者；仅反复描述同一来源没有额外价值。
6. 处理空候选集合、模型外异常、观察模糊、缺少规程、用户不能执行和状态空间超限。
7. 对允许结论再检查独立的功能复测与来源等级条件，防止局部外观推断绕过结果契约。

首版候选状态建议上限 64、检查上限 8，这只是实现预算，不是性能保证。超限返回受限处理/人工，不能删掉不利状态获得“已恢复”。包含设备操作的检查不是无副作用查询，必须执行一步后重新规划。

**关键设计修正：** 某检查不消除反例，却是验效规程强制项时仍须执行。不能仅因为区分分数为零就跳过必要功能复测；“必要规程”和“可选信息增益”分别处理。

### 7.5 历史记录与隐私

同一用户可查看自己的历史会话；客服仅查看被授权的工作队列或会话；公开知识只能使用审核脱敏案例。未经授权的跨用户历史不进入检索。

交接摘要由结构化记录生成：产品、症状、已执行动作、未确认信息、失败检查、引用证据、当前结果等级。AI 可润色，但不得将“用户自述”改写成“已证实”。

### 7.6 内部人工工作台

首版必须实现真实队列、原子接单、追加消息、请求补充信息、记录处理结果及关闭/重新打开。两名客服同时接单时只能一人成功，失败方看到最新状态。

客服接管后 AI 暂停自主推进操作，仅作为建议辅助。重新交回自动流程须显式记录，旧 Worker 输出不得覆盖客服操作。

这使系统无需等待企业 API 也能真实闭环。企业接口适配不与人工工作台混成一个假按钮。Chatwoot 等外部接入需要远端真实会话回执，并区分远端创建、分配与接单。 [外部会话 API 参考](https://developers.chatwoot.com/api-reference/conversations/create-new-conversation)

### 7.7 渠道凭证与质保路径

建立购买渠道、凭证附件和核验状态，不自动裁定质保。订单查询适配器必须区分 `MATCHED`、`NOT_FOUND`、`UNAVAILABLE`、`UNAUTHORIZED` 和 `ERROR`。

无官方接口时，只提供材料收集及人工核对。测试商家列表标注为测试数据；运营方自行维护的真实名录标注来源和更新时间，不自称官方授权名录。

## 8. 接口契约与代码组织

### 8.1 关键 API

| 接口 | 返回的真实结果 | 关键约束 |
| --- | --- | --- |
| `POST /api/v1/cases` | 新会话 ID、初始版本 | 当前用户实际拥有该会话 |
| `POST /api/v1/cases/{id}/messages` | 输入事件与后台 run ID | 幂等键、版本检查、内容限长 |
| `POST /api/v1/cases/{id}/assets` | 已写入素材的 ID 与解析状态 | 文件内容校验、会话归属、非公开存储 |
| `POST /api/v1/cases/{id}/product-confirmations` | 产品确认事件与新版本 | 变更产品需要重审既有证据与步骤 |
| `POST /api/v1/actions/{id}/reports` | 操作反馈事件 | 只能报告当前会话具体动作，不直接改结果 |
| `POST /api/v1/checks/{id}/results` | 观察候选或受控适配结果 | 客户端无权自定可信等级 |
| `GET /api/v1/cases/{id}` | 版本、任务、结果等级与状态 | 前端以此为准，不维护另一套结论 |
| `GET /api/v1/cases/{id}/events?after=...` | 可恢复的会话事件 | 鉴权、事件顺序、脱敏 |
| `POST /api/v1/cases/{id}/handoffs` | 真实内部服务单号 | 用户确认后创建；外部未提交不可冒充回执 |
| `POST /api/v1/tickets/{id}/accept` | 人工接单事件 | 客服角色、原子竞争检查 |
| `POST /api/v1/tickets/{id}/messages` | 实际追加消息 | 用户端和客服端读取同一记录 |
| `POST /api/v1/tickets/{id}/resolutions` | 处理结果和证据 | 人工权限、结果等级边界、关闭原因 |
| `POST /api/v1/admin/documents/imports` | 导入任务 ID | 受限文件/URL、后台执行 |
| `POST /api/v1/admin/packs/{id}/publish` | 审核通过的不可变版本 | 审核角色、验证报告与来源完整性 |

所有写接口使用一致错误结构，包括 `code`、`message`、`retryable`、`trace_id`。版本冲突返回 409；授权失败不能伪装成空数据成功。OpenAPI 生成前端客户端，减少手写字段漂移。

## 9. 开发阶段与依赖

### 9.1 阶段划分

| 阶段 | 目标 | 必须交付的端到端结果 | 预计核心开发工时 |
| --- | --- | --- | --- |
| P0：依赖与资源验证 | 清除环境、模型、资料和规则风险 | 模板基础测试、真实模型最小请求、恢复技术试验 | 12 人时 |
| P1：第一条真实会话 | 输入能实际保存并恢复 | 双用户隔离、图片上传、持久会话、后台任务回显 | 24 人时 |
| P2：理解与知识 | AI 根据真实输入与适用资料工作 | 产品澄清、真实检索、候选提取与单步指导 | 29 人时 |

| P5：试用与交付 | 非理想条件下仍可靠运行 | 安全、恢复、保留集、实机试验、部署与备份恢复 | 40 人时 |

| T34 / A / 5 | 部署、迁移、备份与恢复 | 干净环境能启动，备份实际恢复，回滚不丢已提交事件 | T29+T30；隔离环境演练 |

以上人时为任务级基准估计，不含表外变更。若某个任务需修改超过约五个主要模块，先按数据、业务与界面三个可验收子任务拆解，不能把大任务一口气做完再测试。

### 9.3 不可跳过的阶段验收

- G0：T01-T04 完成。模板、真实模型、资料范围、持久恢复均有证据。没有 G0，不进行大量页面开发。
- G1：P1 完成。真实用户输入和文件可保存、恢复、隔离；不接受仅浏览器本地存储的会话。
- G2：P2 完成。真实图片与资料能走到受控步骤；无来源动作和模糊图误判有负向测试。
- G3：P3 完成。反例、结果等级和不可验证出口真正影响后台行为，不只是解释文字。
- G4：P4 完成。两个真实账号完成交接、接单与续聊，自动流程不能覆盖人工。
- G5：P5 完成。安全、故障恢复、备份恢复、保留集和受控实机条件满足后，才进入 L2 试用。

### 9.4 并行与串行关系

A 先固定权限、会话与事件接口；B 可同时审核资料并完成真实模型试验；C 先建立模板交互和端到端测试框架。接口确定后再并行做各个纵向流程。

迁移、核心状态类型和契约模式必须指定一个负责人合并。不得同时各自建立一套会话状态，也不得让前端以临时假结构长期推进。前端短期测试夹具可以使用，但要有清晰测试标识、对应真实接口任务和删除日期。

## 10. 24 小时赛场版与近期安排

### 10.1 24 小时要交付什么

现场目标是 L1 的最小闭环：单型号、一个故障族、审核后的少量步骤、真实模型、真实数据库、核心反例用例、内部人工接单。它不是把 L2 全部任务压缩到 24 小时。

| 时间 | A：平台 | B：AI 与验效 | C：交互与测试 |
| --- | --- | --- | --- |
| 0-4 小时 | 环境、身份、会话与数据库 | 模型试连、资料范围和契约 | 用户入口、上传与 API 测试骨架 |
| 4-8 小时 | 文件、后台任务与事件 | 真实理解、产品澄清与检索 | 接通真实输入、产品确认和状态恢复 |
| 8-14 小时 | 动作记录、内部工单与版本控制 | 动作影响、反例与限定复测 | 步骤反馈、结果依据和精简客服队列 |
| 14-18 小时 | 接单、续聊与异常回执 | 失败、未知、无法执行分支 | 双账号交接与三类题目故事 |
| 18-22 小时 | 恢复、权限与部署检查 | 核心反例和真实模型冒烟 | 桌面/手机、弱网、重复提交 |
| 22-24 小时 | 冻结并验证启动 | 核对真实性和演示依据 | 全流程演示与备份材料 |

此排程要求成员熟悉技术栈、有可用账号和审核资料，且开源复用方式符合赛事要求。若条件不具备，必须缩小承诺，不隐藏失败。

24 小时可缩减项：知识后台先用受控导入命令和人工审核记录；历史检索先限本人历史；仅一个模型供应商；文件先用私有持久卷；复杂统计、外部平台连接和第二产品不进入关键路径。

24 小时不可缩减项：真实请求与存储、资源授权、来源、未知出口、结果等级、内部真实接单、超时/重复提交/重启的基本测试。否则只能标为技术演示，不标为可用服务。

### 10.2 与赛事时间对应

本轮官方页面列出 9 月 27 日预赛材料截止、10 月 16-17 日现场 24 小时开发。页面顶部状态与日期存在明显不一致，因此只将明确赛程文字作为当前安排参考，最终以组委会通知为准。 [赛事页面](https://career.anker.com.cn/hackathon/)

## 11. 验收与测试计划

### 11.1 不接受的“假完成”

| 表面表现 | 为什么不算完成 | 必须补充 |
| --- | --- | --- |
| 聊天有回复 | 可能是固定字符串或历史录制 | 真实输入对应的模型 run、检索证据与响应记录 |
| 图片显示在页面 | 可能只保存在浏览器内存 | 服务端文件、授权读取、刷新后可见 |
| 页面显示“已完成” | 可能只是按钮改了前端变量 | 后台决策记录、输入版本与允许条件 |
| 页面显示“已转人工” | 可能没有任何人能接到 | 内部服务单、另一账号实际接单及续聊 |
| 重启后能打开首页 | 不证明会话恢复 | 已提交事件、图片和当前动作继续存在 |
| 自动化测试全绿 | 可能都是 mock | 真实 PostgreSQL、真实模型冒烟和无业务拦截的端到端记录 |

### 11.2 必测异常

| 用例 | 应有行为 |
| --- | --- |
| 相同简称对应不同品类 | 先澄清，不进入错误产品步骤 |
| 图片模糊、局部不可见 | 保留未知，不补出隐藏事实 |
| 同一图片和 OCR 多次到达 | 去重或归同源，不重复累计可信度 |
| 操作后重传旧图片 | 不因上传时间新就证明当前状态；顺序未知则降级 |
| 用户只执行一部分 | 不直接应用完整动作结果 |
| 无影响的产品身份信息 | 仍可复用，不要求用户重新填写全部信息 |
| 外观改善，功能仍异常 | 反例仍存在，不能高等级结案 |
| 所有候选被相互矛盾观察排除 | 输出冲突，不利用空集逻辑放行 |
| 必要复测的选证增益为零 | 仍执行必要规程，不被优化器跳过 |
| 功能检查不可获得 | 待验证或转人工，不循环索要同样素材 |
| 用户甲请求用户乙的素材/会话 | 拒绝访问并记录安全事件 |
| 客户端自行设置可信等级 | 忽略或拒绝字段，不能提升等级 |
| 模型或资料要求越权调用 | 工具白名单阻断，不执行隐藏指令 |
| 模型超时、限流、格式错误 | 有限重试、清晰降级、会话不丢失 |
| outbox 已写但任务未投递即退出 | 恢复后可继续，不丢提交 |
| 外部建单成功但本地未收到结果 | 标记待核对，不盲目重复建单 |
| 客服接管时旧模型请求返回 | 旧请求不得继续执行或覆盖人工状态 |
| 两人同时接单 | 只有一人成功，另一个收到状态冲突 |
| 知识或契约被撤回 | 不再推荐相关步骤，旧引用仍可审计 |
| 备份恢复到隔离环境 | 会话、素材、知识版本与当前步骤一致 |

### 11.3 数据集与指标

先准备不少于 30 条审核的结构化过程用例、20 条图文保留样例和 12 条完整服务故事，作为工程回归起点。这些数量是最低开发覆盖目标，不足以证明总体维修有效率。

开发集与保留集按会话、设备和原始图片来源划分，避免相同素材变体泄漏。真实产品样本、人工构造样本和模拟物理结果分别标记，不能混在一个“成功率”里。

真实图文样本不足时阻断对应识别能力验收；不能用生成图片补齐后声称完成实机识别验证。实机试验由独立记录者记录实际执行和结果，用户对话内容不是唯一真值。

指标包括错误结案率与其分母、结案覆盖率、错误品类路由、无依据动作、实际取证时间、重复步骤、人工接手后的补问量、任务恢复率和每会话模型成本。全部转人工不能算“零错误且效果优秀”。

比较三个基线：相同模型与资料的检索客服、带必要复测的审核固定流程、具有状态维护但不做反例选证的工作流。若简单固定复测同样可靠且更省事，就简化主动规划，保留有效机制。

### 11.4 性能目标及测量条件

先以单组织、10 个同时活跃会话进行试用压测，服务器规格、模型供应商和网络单独记录。建议首轮目标：不含文件传输与模型耗时的写入确认 P95 小于 1 秒，普通状态查询 P95 小于 500 毫秒；模型理解请求设置可配置超时，暂以 45 秒为试验值。

这些是待验收目标，不是当前成绩。服务时间与模型时间分别统计；不能用合成逻辑 4 毫秒运行时间宣称整体回复速度。超过预算或模型限流时明确排队、降级或转人工。

## 12. 安全、部署与运营

### 12.1 安全必做

- 邀请制账号与明确角色；首版不开放无限注册，不沿用示例超级用户口令。
- 保留成熟认证基础并审查浏览器令牌存储；试用版优先受保护 Cookie 会话，配套 CSRF、同源约束、过期与注销失效，不在日志输出凭证。
- 文件大小、像素数量、实际格式、解码与访问路径校验；普通用户只传允许的图片，管理文档走隔离解析。拒绝可执行内容和任意路径读取。
- 原始素材默认私有，按保留期删除；对外模型只发送完成任务所需的最小内容，预先告知处理范围。默认不将真实素材发送到公共追踪平台。
- 资料导入限制 URL 与跳转，不允许 SSRF；返回 Markdown 做链接、脚本与 HTML 安全处理。
- 模型工具严格白名单；禁任意 SQL、命令、网址访问和自由写业务状态。
- 公网不暴露数据库、调试管理器、开发邮件服务或代理控制台；上线前审查上游 Compose 的默认暴露方式与 Docker socket 挂载权限。
- 配置依赖漏洞与密钥扫描；高风险问题未处理不得进入真实用户试用。开源项目受欢迎不等于没有漏洞。

### 12.2 运行可靠性

应用事务与 outbox 保证本地事件不因投递窗口丢失；队列按至少一次处理设计，业务按幂等执行设计。不能向用户承诺任意远端系统恰好执行一次。

外部写操作必须持有授权及确认记录；对方无幂等能力时使用可回查业务键和人工核对，不在未知结果时盲目重试。人工接管与新的输入优先于旧任务。

知识更新、数据库迁移和应用发布分开：迁移任务由单独受控步骤执行，不让每个 Worker 启动都重复迁移。发布前备份，采用尽量兼容前后版本的迁移；破坏性迁移需独立审批。

### 12.3 部署与恢复

本机开发优先 Docker Linux 容器；在线应用与 Worker 共用同一已构建镜像。初期 PostgreSQL 与私有文件卷都须纳入备份；只有数据库备份而没有素材不算可恢复。

试用前在另一份隔离数据目录恢复一次，校验事件数量、关键素材哈希、契约版本和未完成会话。记录实际恢复时长与可接受的数据损失窗口，未经演练不填写“已支持灾备”。

目标脚本入口：`doctor.ps1` 检查配置，`dev-up.ps1` 启动开发，`verify.ps1` 运行核心验收，`backup.ps1`/`restore.ps1` 处理备份恢复。脚本尚待开发；它们应拒绝未确认的生产目标，不能包含自动清空用户数据操作。

### 12.4 运行观测与成本

最低观测字段：`trace_id`、`case_id`、`event_id`、模型版本、提示版本、知识版本、输入/输出用量、耗时、重试次数、决策原因及错误码。日志默认脱敏，只保存必要的请求摘要和素材引用。

设置每会话、每用户和每日模型预算上限；上限按实际供应商计费与试用预算确定，不写虚构价格。禁止无上限自我反思、多 Agent 循环调用和无限重试。

Langfuse 等平台后续用于观测，不成为业务事实来源；观测系统不可用时，核心服务仍能按受控方式继续。

| 试用域名、主机与隐私规则 | T34 前 | 保持本地或受控内网，不提前宣称上线 |

密钥通过本机未提交配置或受控密钥管理提供，不要求在聊天、截图或公共文档里直接粘贴。

### 13.2 主要风险与退出策略

| 风险 | 预警 | 应对 |
| --- | --- | --- |
| 新版本依赖不兼容 | 容器解析失败、检查点包冲突 | G0 固定兼容组合，必要时选择经验证的模板历史基线，不随意改大版本要求 |
| 队列维护与兼容风险 | 上游维护人不足、恢复试验不通过 | 锁定已验证版本，隔离 `JobRunner` 接口；不通过则替换经过验证的队列，不自行临时手写完整调度器 |
| 视觉能力不够 | 保留集频繁将未知写成已知 | 限制可提取观察、加强纠正与人工确认，不靠提高“置信度阈值”掩盖问题 |
| 真实故障模型难以确定 | 大量候选无法审查或互相矛盾 | 减少承诺范围，以安全指导、限定结果和人工处理为主 |
| 核心变成全部拒绝 | 错误率低但覆盖率接近零 | 同时看覆盖率和负担，优化资料与可执行复测，而非包装零错误 |
| 前端推进快于后台 | 大量业务按钮使用固定返回 | 每个界面绑定 API、任务编号和验收用例；未接通时不显示成功 |
| 第三方接口不可得 | 申请迟迟未获批准 | 内部工单闭环独立完成；外部接口不放在核心创新前置依赖上 |
| 赛期不够 | 16 小时仍无完整服务链 | 停止新增界面，完成单场景与失败交接；如实标注未完成能力 |

## 14. 首日执行顺序与最终交付

### 14.1 第一天先做这六件事

1. 确认赛事允许的复用与开发范围，建立代码来源记录。
2. 固定模板提交，在容器中运行上游基础测试；不先重新设计首页。
3. 用真实模型跑一段描述和一张设备图片，保存有效请求与失败请求记录。
4. 在真实 PostgreSQL 中保存一个会话与一张图片，重启后能恢复。
5. 用两名用户验证资源隔离，再做一次后台任务中断恢复。
6. 完成一份审核服务包草案，确认哪些信息可观察、哪些结论必须保留待验证。

第一天的成果应当是“环境与真实链路是否成立”的明确答案，而不是十几个空页面。

### 14.2 L2 交付包

- 可复现应用源代码、依赖锁文件、容器构建与部署配置。
- 开源来源清单、许可证/NOTICE、实际改动说明与供应链检查结果。
- 版本化产品服务包、知识来源映射、审核记录与撤回方式。
- 自动化测试、真实模型冒烟、双账号闭环、故障恢复与备份恢复记录。
- 保留集定义、对照结果及未通过用例，不删除不利结果。
- 实机试验的条件、观察、结果和不能外推的边界。
- 用户、客服和管理操作说明；明确服务责任人、异常处理及停用方式。
- 当前已实现/未实现/不支持清单；真实业务接口与模拟内容分开。

### 14.3 最终完成判断

第三人不依赖开发者口头说明，能够从干净环境启动系统，用两个账号完成“求助、图片、澄清、指导、反馈、验效、转人工、接单与续聊”，遇到失败知道状态与下一步；开发者能从后台说明每个结果为什么成立，并能恢复一次备份。

满足这一标准，才可以说做出了受限但真实可用的售后系统。物理维修有效性和企业上线资格，分别依据实机试验和企业验收，不由界面完成度代替。
